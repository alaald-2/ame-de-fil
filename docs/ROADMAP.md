## Phase 4 — Klarna & Swish, fulfillment lifecycle 🟡 in progress

Klarna/Swish payment methods via Stripe (ADR-014), shipment tracking via `ManualShippingProvider` (admin-entered, carrier-agnostic — ADR-022), made-to-order production-time flow, transactional email (order confirmation, shipping notification), abandoned-checkout handling.

**Klarna: implemented and verified live** (`DECISIONS.md` ADR-028) — `StripePaymentProvider` now offers `card`+`klarna` via an explicit `payment_method_types` list (matching ADR-014, not the prior `automatic_payment_methods` config). A real checkout through Klarna's actual test-mode sandbox redirect/confirmation flow was run end-to-end, confirming correct order/payment state transitions, inventory movement, and the storefront's existing Payment Element rendering Klarna with no frontend code change needed. `Payment.method` (previously unpopulated) now records which method was actually used, via a new `charge.succeeded` webhook handler.

**Swish: blocked, not a code gap.** Verified live that this Stripe account's Dashboard has not activated Swish — Stripe's API rejects it outright (`"not activated in your dashboard"`), a bank-linked Swedish payment method likely requiring Stripe's own approval. The code is ready: adding `"swish"` to `ENABLED_PAYMENT_METHOD_TYPES` (`stripe-payment.provider.ts`) is the only change needed once activated — no other code, webhook, or frontend work required, since the same generic Stripe PaymentIntents/webhook/Payment Element path already handles it identically to Klarna.

**Shipment tracking: implemented** (`DECISIONS.md` ADR-029) — admin endpoints for `CONFIRMED → READY_TO_SHIP → SHIPPED → DELIVERED`, with carrier name/tracking number recorded on `Shipment` (`ManualShippingProvider`'s admin-entered model, ADR-022). The `IN_PRODUCTION` branch for made-to-order items is deliberately not built here — see the next item — and there's no admin UI yet (Phase 5's "order management" scope will call these endpoints).

**Made-to-order production-time flow: implemented** (`DECISIONS.md` ADR-030) — orders with made-to-order lines land on `IN_PRODUCTION` instead of `CONFIRMED` at confirmation time (`OrderItem.madeToOrder`/`productionTimeDaysSnapshot`, snapshotted at checkout), and `markReadyToShip` accepts `IN_PRODUCTION` as a predecessor alongside `CONFIRMED`. Verified live end-to-end (real checkout → real webhook → `IN_PRODUCTION` → admin `ready-to-ship`), plus a regression check that ready-to-ship-only orders are unaffected. Not built: an "estimated ready date" computed/surfaced anywhere — a Phase 5 display concern layered on the now-persisted `productionTimeDaysSnapshot`, not state-machine work.

**Transactional email: implemented** (`DECISIONS.md` ADR-031) — `packages/email` (bilingual `sv-SE`/`en` React Email templates for order confirmation and shipping notification) and `apps/api/src/notifications` (`NotificationsService`, an `EmailProvider` abstraction resolving to generic SMTP or a `PendingEmailProvider` fallback). Dispatched synchronously, post-commit, from `PaymentsWebhookService` (on `CONFIRMED`/`IN_PRODUCTION`) and `AdminOrdersService.markShipped`. **Real vendor selection remains deferred** — this checkpoint ships a Mailpit local-dev catcher (`docker-compose.yml`) and the generic-SMTP dispatch mechanism, not a chosen production vendor; the DPA `docs/SECURITY.md` §10 already flags for "the email provider" still applies once one is actually chosen. Also not built: durable retry across a process crash between commit and send (no BullMQ/outbox — ADR-031 documents this limitation directly rather than treating synchronous post-commit dispatch as crash-proof).

**Abandoned-checkout handling: implemented** (`PAYMENTS.md` §7) — `PENDING_PAYMENT` orders whose reservation expires without a `PAID` webhook are canceled automatically via the existing `ReservationExpiryScheduler`/`ReservationExpiryService` (`DECISIONS.md` ADR-025), which already covered the common case. This checkpoint closed the one gap in that mechanism: a fully made-to-order order (every line `tracksStock: false`) never gets a `StockReservation` at all, so it was invisible to the sweep and could sit in `PENDING_PAYMENT` forever regardless of age. `ReservationExpiryService` now also finds and cancels `PENDING_PAYMENT` orders past `CHECKOUT_RESERVATION_TTL_MINUTES` (measured from `Order.createdAt`) with no reservation on any line, folded into the same `canceledOrders` count the endpoint/scheduler already report — no new config, permission, or API field. Verified against real Postgres, including that a mixed order (some tracked, some made-to-order lines) is still only ever canceled by its own reservation expiring, never double-processed. **Deliberately not built:** any customer-facing "abandoned checkout" or "abandoned cart" recovery email — `PAYMENTS.md` §7 already scopes that as a separate, unconfirmed feature, distinct from this cancellation mechanism.

**Real auth entry point: implemented** (`DECISIONS.md` ADR-032) — `AuthController`/`AuthService` (`POST /auth/login`, `POST /auth/logout`, `GET /auth/session`) built directly on the pre-existing `SessionService`/`PasswordService`/`SessionAuthGuard`/`PermissionsGuard`/`CsrfGuard` (Phase 1's "auth core... skeleton", ADR-015), none of which changed. Every admin-only route shipped so far (`admin/products`, `admin/inventory`, `admin/checkout`, `admin/orders`) is now reachable by a real client with a real session, verified live against the real running API. **Deliberately not built:** self-service *password* registration and password-reset endpoints, MFA, and any admin UI — RBAC/user administration itself remains Phase 5 scope, untouched here.

**Google sign-in: implemented, optional extension** (`DECISIONS.md` ADR-033) — `GET /auth/google`/`GET /auth/google/callback`, Authorization Code + PKCE, scoped to storefront customers (not admin staff). A first-time Google sign-in now auto-creates a `User` with no password at all (`OAuthAccount`, a new additive migration) — this is the one path that *does* create accounts, unlike password login above. **Deliberately not built:** any "Sign in with Google" UI in either frontend (apps/storefront has no auth page at all yet), sign-in with any provider other than Google, and self-service password registration is still nonexistent for the password path. **Not verified against real Google servers** — no Google Cloud OAuth client was available in this environment; verified against a real database and mocked Google responses only, behind a `PendingOAuthProvider` fallback (same posture as Stripe/SMTP) when unconfigured.

## Phase 5 — Admin dashboard 🟡 in progress

Full admin scope from `PRODUCT_SPEC.md` §5: dashboard metrics, order management (incl. refunds), inventory management (reservations/movements/low-stock alerts), customer management, RBAC/user administration, audit log viewer.

**Order management: list/detail implemented** — `GET /admin/orders` (paginated, most recent first) and `GET /admin/orders/:orderId` (full detail: items, payments, shipments, shipping/billing addresses), gated by a new `orders.view` permission, kept separate from `orders.fulfill` (mirrors the existing `inventory.view`/`inventory.adjust` split) so a role can be granted read access without fulfillment authority, or vice versa. Admin-safe by construction: every query uses an explicit `select`, so a `User` row can only ever surface `id`/`email`/`firstName`/`lastName` — verified live that a real password hash never reaches the response. No per-order ownership check (unlike the guest/owner-scoped `OrdersController.getStatus`) — an admin holding `orders.view` is authorized to see any order, not just "their own," so the authorization boundary is entirely the permission guard. **Deliberately not built (at that checkpoint):** refunds, order mutations beyond the existing fulfillment endpoints, dashboard metrics, and RBAC/user administration.

**Order management: refunds implemented** (`PAYMENTS.md` §6) — `POST /admin/orders/:orderId/refund`, amount-based, gated by a new `orders.refund` permission (kept separate from `orders.fulfill`/`orders.view`, same rationale as above). Concurrency-safe by construction: a `SELECT ... FOR UPDATE` lock on the `Payment` row makes the reservation (not a prior read) what a racing concurrent request sees, so two requests can never collectively over-refund — verified with a real-Postgres test running genuinely concurrent requests via `Promise.all`. A second, related race (two different refunds completing near-simultaneously both concluding "restock now" from a stale cumulative-total read) is closed by gating the inventory increment on the row-count of a guarded `Order`-status UPDATE rather than a plain boolean — also verified with a dedicated real-Postgres concurrency test; this second race was caught by that test during implementation, not assumed safe from the locking alone. Stripe's own idempotency key (derived from our own `Refund.id`) makes a resumed attempt after a crash safe to repeat, verified against real Stripe test mode. **Deliberately not built:** per-line-item refund selection, asynchronous/webhook-based refund confirmation (synchronous only — `PAYMENTS.md` §6 discloses the gap), and a background reconciliation job (a bounded, attempt-triggered self-heal exists instead — same section). Order mutations beyond fulfillment+refunds and dashboard metrics remain open Phase 5 scope.

**Customer management: list/detail (view-only) implemented** — `GET /admin/customers` (paginated, most recently registered first) and `GET /admin/customers/:id` (profile detail + recent order history, capped at 10 — `GET /admin/orders` already exists for browsing a customer's full history in depth), gated by its own `customers.view` permission rather than reusing `orders.view` or any other, since none of them are actually about viewing `User`/profile data. `User` also holds staff/admin accounts (there's no separate `Customer` model or `isStaff` flag) — this genuinely lists every `User` row, the same way `GET /admin/orders` lists every order regardless of who placed it. Admin-safe by construction: every query uses an explicit `select`, so `passwordHash`/`totpSecret`/sessions/OAuth links/roles can never reach this response — verified live and in a real-Postgres test that a real password hash and TOTP secret never appear anywhere in either response. **Deliberately not built:** address book, customer notes, any update/delete, and any filtering beyond pagination.

**Audit-log viewer: implemented** — `GET /admin/audit-log` (paginated, most recent first), gated by its own `audit.view` permission rather than folded into any existing view permission (the audit trail reveals other admins' actions and IPs, a distinct, more sensitive privilege — `SECURITY.md` §9). Deliberately a separate `AdminAuditLogService`, not a read method added to `AuditService` itself — that class's own contract is write-only, and every other module depends on that staying true. Resolves the acting admin's email via an explicit `select` on the `actor` relation only (never a bare include), verified live and in a real-Postgres test that a password hash never reaches the response, and that the FK's `onDelete: SetNull` behavior (a deleted actor) resolves to a null actor/email rather than an error. **Deliberately not built:** any update/delete path (the model is append-only by design), filtering by entity/actor/date, and the `apps/admin` UI page that would call this endpoint.

**RBAC/user administration implemented** (`SECURITY.md` §2) — `AdminUsersController`/`AdminRolesController` (`apps/api/src/users/`): `GET/POST /admin/users`, `GET /admin/users/:id`, `POST /admin/users/:id/{activate,deactivate}`, `POST /admin/users/:id/roles`, `DELETE /admin/users/:id/roles/:roleId`, and a read-only `GET /admin/roles` catalog. Three new permissions (`users.view`/`users.manage`/`users.manage_roles`) gate it, mirroring the `inventory.view`/`inventory.adjust` split, with role-assignment/removal deliberately behind the strictest of the three since it's the one escalation-capable action. Staff-scoped throughout (`roles: { some: {} }`, the existing `UserRole` relationship — no new `isStaff` column) so `GET /admin/users` never duplicates `GET /admin/customers`'s full-`User`-table listing; `POST /admin/users/:id/roles` is the one exception, able to target any existing user (including a pure customer) since that's how an account becomes staff in the first place. New admin/staff accounts get a server-generated, Argon2id-hashed password returned once in the creation response — no client-supplied passwords, nothing persisted or logged in plaintext. Privilege-escalation and last-admin-holder protections (self-role-changes blocked completely, role grants capped at the acting admin's own current permissions, a `SELECT ... FOR UPDATE` lock on the `users.manage_roles` `Permission` row serializing every concurrent deactivation/role-removal that could reduce its active-holder count to zero) are detailed in `SECURITY.md` §2 and verified with real-Postgres concurrency tests. **Deliberately not built:** Role/Permission CRUD (creating a role or editing what it grants stays seed-script-only), direct user-level permission overrides (no `UserPermission` table), invitations/self-service password reset (no token/email infrastructure exists or was added), admin-triggered password reset for another user, and the `apps/admin` UI page that would call any of this.

**Dashboard metrics implemented** (`SECURITY.md` §2) — `GET /admin/dashboard?from=<ISO>&to=<ISO>` (`apps/api/src/dashboard/`), a single read-only, cross-domain overview gated by a new `dashboard.view` permission (kept separate from every underlying domain's own `*.view` permission, same rationale as `audit.view`/`customers.view`). Both query params are optional and explicit UTC instants — no named-period presets and no timezone conversion in the API at all (nothing in this codebase does timezone math; a future admin UI, which knows the browser's local timezone, converts "today" to a UTC range before calling this); defaulting to the last 30 days when omitted. Every figure is computed via database-side `count`/`aggregate`/`groupBy`, never a `findMany` reduced in memory. **Revenue is precisely defined, not a single blended number:** gross revenue sums `Order.totalMinor` gated on `confirmedAt` falling in the requested window — using "was this order ever confirmed" rather than a maintained status allow-list, which is what correctly includes `PAYMENT_SUCCEEDED_STOCK_LOST` orders (a real successful payment despite a fulfillment problem, ADR-026) and correctly excludes `DRAFT`/`PENDING_PAYMENT`/`CANCELED` orders (none of which ever get a `confirmedAt`) with no exclusion list to keep in sync as statuses evolve. Refunds are netted out on a **cash basis**: `SUM(Refund.amountMinor)` for `SUCCEEDED` refunds with `processedAt` (not `createdAt`) in the same window — a refund processed today reduces today's net figure even if its original order was confirmed in an earlier period, and never retroactively revises that earlier period's own numbers. Order/payment/refund status breakdowns are period-scoped by `createdAt`; `alerts` (disputed payments, failed refunds, low-stock count) are deliberately **current-state snapshots, unscoped by the requested period** — a chargeback can be filed weeks after the original payment, so period-scoping would hide an old-but-still-urgent one. "Customer" reuses the RBAC checkpoint's own `roles: { none: {} }` staff filter (no new `isStaff` column); guest checkouts are never counted (no `User` row exists for one). `inventory.lowStockCount` reuses `InventoryService`'s exact existing low-stock predicate via a new, purely additive `countLowStock()` method (a bare count, no list — no inventory behavior change). **Schema change**: five new, purely additive indexes (`Order.createdAt`/`confirmedAt`, `Payment.createdAt`, `Refund.createdAt`/`processedAt`) — every dashboard query filters on one of these, previously unindexed. Verified against real Postgres for every edge case: the half-open interval boundary (`confirmedAt === from` included, `=== to` excluded), the cross-period refund-netting scenario above, an empty period returning all zeros with a `null` average order value, and alerts correctly ignoring the requested period entirely. **Deliberately not built:** named-period presets, day-by-day time-series data, a caching layer, drill-down list endpoints for any alert, staff/admin user counts (that's `GET /admin/users`), and the `apps/admin` UI page that would call this.

**Inventory management: low-stock alerts implemented** — `GET /admin/inventory/low-stock` (paginated, most urgent — lowest `onHand - reserved` — first), reusing the existing `inventory.view` permission (list/detail/adjust already lived behind it; this is the same authorization boundary, not a new one) and the existing `inventoryItemResponseSchema` response shape (no new DTO). Only finite-stock items (`tracksStock: true`) with a `lowStockThreshold` actually set can ever qualify — a made-to-order line has no ceiling to run low on, and a `null` threshold has nothing to compare against. `"onHand - reserved" < "lowStockThreshold"` compares two columns to each other, which Prisma's declarative `where` filters can't express at all — a parameterized raw SQL query (`Prisma.sql`, the same escape hatch `stock-lock.ts` already uses for the identical class of problem) finds the matching, paginated ids first, then an explicit `select` shapes them for the response. Verified against real Postgres for every boundary case: exactly-at-threshold (correctly excluded, strict `<`), one-under (included), no-threshold-set (excluded regardless of stock level), `tracksStock: false` (excluded regardless of stock level), and negative availability from overselling (included, and correctly ranked most urgent). **Deliberately not built:** any mutation, notification/email, admin UI surface, or filtering beyond pagination. (A bare low-stock *count*, not this list, is now also surfaced via `GET /admin/dashboard` — see the dashboard-metrics entry above.)
