## ADR-001: Package manager — pnpm ✅

**Decision:** pnpm (workspace protocol + catalogs) for dependency management.
**Alternatives:** npm workspaces, Yarn Berry.
**Why:** content-addressable store gives fast, disk-efficient installs across many packages; strict node_modules prevents phantom dependencies, which matters in a monorepo with shared `packages/`; pnpm `catalog:` entries let every app pin the same React/TypeScript version from one place.
**Consequences:** contributors must use pnpm (enforce via `packageManager` field in root `package.json` and `only-allow`). Pin the exact version installed locally via `packageManager: "pnpm@12.3.4"`.

## ADR-002: Monorepo orchestration — Turborepo ✅

**Decision:** Turborepo 2.10.x on top of pnpm workspaces.
**Alternatives:** Nx (more powerful but heavier, opinionated generators we don't need), Bazel (over-engineered for a 3-app monorepo), plain pnpm scripts (no caching/graph awareness).
**Why:** minimal-config task graph + local/remote caching, native pnpm support, small learning curve, Vercel-maintained and Next.js-aligned.
**Consequences:** need a shared remote cache (Vercel Remote Cache or self-hosted) in CI for the caching benefit to pay off — tracked in `DEPLOYMENT.md`.

## ADR-003: Frontend framework — Next.js 16 (App Router) ✅

**Decision:** Next.js 16.x, App Router, Turbopack (default bundler), React 19.2, Server Components by default.
**Alternatives:** Remix (weaker RSC story), Astro (weaker for a highly interactive cart/checkout), plain Vite SPA (loses SSR/SEO for free).
**Why:** first-class SSR/RSC for SEO-critical product/category pages, built-in image optimization, Metadata API for structured SEO, mature App Router (stable since 2024, now the default recommendation for new projects in 2026), Turbopack default build speed.
**Consequences:** two Next.js apps (`storefront`, `admin`) — admin does **not** need SEO/SSR-heavy treatment but shares the same framework for tooling/DX consistency and to reuse `packages/ui`.

## ADR-004: Styling — Tailwind CSS v4 ✅

**Decision:** Tailwind CSS v4.3.x, CSS-first configuration (`@theme` in CSS, no `tailwind.config.js` needed).
**Why:** v4's rewritten engine (5x faster full builds, 100x faster incremental) matters for a large monorepo; CSS-first theme tokens map cleanly onto a design-token driven brand system (see `DESIGN_SYSTEM.md`).
**Consequences:** design tokens (color, type scale, spacing) are defined once in `packages/config` and consumed via `@theme` imports in both `storefront` and `admin`.

## ADR-005: Component layer — shadcn/ui (code-owned) ✅

**Decision:** shadcn/ui as a source generator (components copied into `packages/ui`, not an npm runtime dependency), built on Radix primitives.
**Alternatives:** MUI/Chakra/Ant (too opinionated visually — reads as "generic AI-generated SaaS", exactly what the brief says to avoid), headless Radix/Ariakit from scratch (more work, no gain since shadcn already **is** that).
**Why:** because the components live in our repo, every visual default (radius, shadow, spacing, motion) is fully overridable — essential for a bespoke premium-atelier look rather than a template look. Accessibility (Radix) is inherited for free.
**Consequences:** the design system doc (`DESIGN_SYSTEM.md`) governs how far components are restyled from shadcn defaults — the brief explicitly bans "excessive rounded cards" and "excessive shadows", which are shadcn's _defaults_, so restyling is mandatory, not optional polish.

## ADR-006: Motion — Motion (formerly Framer Motion) v12 ✅

**Decision:** `motion` package, imported via `motion/react`.
**Why:** Framer Motion was renamed/spun out as an independent project ("Motion") in 2025; the old `framer-motion` package still works but is no longer actively developed. Start clean on the maintained package.
**Consequences:** motion use is restrained per brand direction — page-transition and micro-interaction use only, no decorative animation. Respect `prefers-reduced-motion` everywhere (WCAG 2.2 AA requirement).

## ADR-007: i18n — next-intl ✅

**Decision:** next-intl 4.14.x for both `storefront` and `admin`.
**Alternatives:** next-i18next (Pages Router legacy, weaker RSC support), Lingui, Intlayer, rolling our own.
**Why:** built for the App Router from the ground up — Server Component translation with no client-bundle cost, native `[locale]` segment routing, typed message keys.
**Consequences:** locale routing is `/{locale}/...` with `sv-SE` as default/fallback and `en` as the one sibling locale — **`fr-FR` removed entirely** per your 2026-09-08 confirmation (ADR-021: Sweden-only market). Admin (`apps/admin`) is also bilingual `sv-SE`/`en` for staff, per the same confirmation. Product/category/collection **content** (not just UI strings) needs its own translation tables in the database — see `DATABASE.md`; next-intl only covers UI copy, not CMS-style content.

## ADR-008: Backend framework — NestJS 12 ✅

**Decision:** NestJS 12.x (TypeScript, modular DI architecture).
**Alternatives:** Express/Fastify raw (no structure at this scale), Fastify-only (less batteries for RBAC/validation/module boundaries), tRPC-as-backend (rejected — see ADR-011).
**Why:** enforced module boundaries map naturally onto commerce domains (catalog, cart, orders, payments, inventory, identity, admin); first-class Swagger/OpenAPI generation; strong DI makes provider abstractions (`PaymentProvider` ADR-014, `ShippingProvider` ADR-022) and testability straightforward; NestJS 12 is ESM-ready and Node 24 compatible.
**Consequences:** the API is REST/OpenAPI, not GraphQL/tRPC (ADR-011).

## ADR-009: ORM & database driver — Prisma ORM 7 ✅

**Decision:** Prisma ORM 7, using the GA Rust-free (TypeScript/WASM query compiler) engine.
**Alternatives:** Drizzle (lighter, less migration tooling maturity for a team-scale schema like this), raw SQL/Kysely (loses schema-driven type generation and migration DX).
**Why:** Prisma 7's Rust-free client removes the native-binary dependency entirely — smaller Docker images, no more `openssl`/musl binary-target pain in CI or Alpine containers, up to 3.4x faster queries by removing cross-language serialization. Given deployment is still open (ADR-020), removing the native-binary/runtime-compatibility risk is valuable.
**Consequences:** pin `prisma`/`@prisma/client` ≥ 6.16 (Rust-free GA) or 7.x once fully released — treat this as **unverified against a primary source** (npm registry / prisma.io release notes) until checked directly at Phase 1 start; do not pin a version from this document without that check.

## ADR-010: Database engine — PostgreSQL 18 ✅

**Decision:** PostgreSQL 18.x.
**Why:** relational integrity is non-negotiable for money, stock, and orders (the brief is explicit: never trust client-supplied totals/stock). Postgres gives us both `SERIALIZABLE` isolation and row-level locking as available tools for inventory concurrency — **`DATABASE.md` §4 is authoritative on which is actually used** (row-level `FOR UPDATE` locks under `READ COMMITTED`, with `SERIALIZABLE` reserved as a fallback), native JSONB for flexible product attributes, and mature extensions (`pg_trgm` for search, `citext`, etc.).
**Consequences:** none of the "NoSQL for catalog flexibility" temptation — product attribute flexibility is handled via a typed `ProductOption`/`ProductOptionValue` model plus JSONB for genuinely unstructured fields (e.g. care-instruction rich text), not by moving the whole catalog to a document store.

## ADR-011: API contract style — REST + OpenAPI (not GraphQL/tRPC) 🟡

**Decision:** REST endpoints documented via NestJS's built-in Swagger/OpenAPI module; a typed client is generated into a shared package for `storefront`/`admin` consumption.
**Alternatives:** GraphQL (overkill — no multi-client under-fetching problem to solve at this scale, adds a resolver/complexity layer), tRPC (very appealing in an all-TypeScript monorepo, but fits a lightweight function-based backend better than NestJS's controller/DTO-based architecture; also we anticipate 3rd-party consumers — Stripe/Klarna/Swish webhooks, and possibly a future mobile app — where a language-agnostic OpenAPI contract pays off more than tRPC's TS-only type sharing).
**Revisit at scale:** if a future native mobile app or partner integrations need a fully-typed contract without hand-written DTOs, re-evaluate tRPC for _internal_ admin-only calls specifically.

## ADR-012: Cache & queue backing store — Valkey (not Redis) ✅

**Decision:** Valkey (Linux Foundation, BSD-3-Clause, Redis-protocol-compatible fork) for caching, rate-limiting, session lookup, and as the BullMQ backing store.
**Alternatives:** Redis (relicensed from BSD to SSPL/RSALv2 in March 2024; as of May 2025 Redis offers a tri-license including AGPLv3, but AGPLv3's copyleft terms are a poor fit for a commercial hosted product without legal review).
**Why:** Valkey is fully open-source (BSD-3), drop-in protocol-compatible with Redis, backed by the Linux Foundation with AWS/Google/Oracle contributing, and is explicitly the pragmatic default for teams starting fresh in 2026. BullMQ supports it today (via the ioredis-compatible protocol, with a dedicated Valkey Glide adapter available).
**Consequences:** any library assuming "Redis" by name (docs, Docker images) is aliased to Valkey; connection strings/env vars are named `CACHE_URL`/`QUEUE_URL` rather than `REDIS_URL` to keep the door open.

## ADR-013: Background jobs — BullMQ 6.x ✅

**Decision:** BullMQ for delayed jobs (stock-reservation expiry, abandoned-checkout follow-up, webhook retry/backoff, transactional email dispatch, low-stock alert digests).
**Why:** mature, well-documented, works with Valkey, supports delayed/repeatable jobs and dead-letter handling needed for reservation expiry and payment reconciliation.
**Consequences:** workers run as a Nest **standalone application context** inside `apps/api` initially (not a separate `apps/worker`), to keep the monorepo surface minimal; split into a dedicated app only if independent worker scaling is needed post-launch.

## ADR-014: Payments — Stripe as unified PSP for Card, Klarna, and Swish ✅ — **confirmed 2026-09-08**

**Decision:** Implement the `PaymentProvider` abstraction as specified in the brief, but for v1, route **all three** payment methods (card, Klarna, Swish) through a single `StripePaymentProvider`, using Stripe's Payment Intents API with `payment_method_types: ['card', 'klarna', 'swish']`. **You confirmed this explicitly** ("Payments: Stripe → Card + Klarna + Swish") — no longer pending.
**Why this changes the brief's literal reading:** Stripe has first-class, documented support for both Klarna and Swish as payment methods on the _same_ Payment Intents API used for cards — same webhook stream (`payment_intent.succeeded`, etc.), same signature verification, same reconciliation surface, same PCI scope. Building three separate merchant integrations (direct Klarna API + direct Swish API with its PKI merchant certificate process) triples the integration surface, webhook handling, and reconciliation logic for v1 with no functional benefit to the customer.
**Alternatives:** direct Klarna Merchant API + direct Swish API (Swish requires a PKI client-certificate enrollment process with the merchant's bank) — kept as a documented future path, not built now.
**Consequences:** the `PaymentProvider` interface stays provider-agnostic (`KlarnaPaymentProvider`/`SwishPaymentProvider` as _named implementations_ is deferred until there's a business reason — e.g. materially better fees at volume, or a Klarna/Swish feature Stripe doesn't proxy). This satisfies the spirit of "not coupling the order system to one provider" (the abstraction exists, order/payment state machines don't know about Stripe) while keeping v1 to a single PSP integration.
**Note:** Swish does not support recurring/off-session payments (irrelevant for v1, no subscriptions in scope).

## ADR-015: Authentication — hand-rolled session auth in NestJS, not a library ✅

**Decision:** Server-owned, cookie-based session authentication implemented directly in `apps/api` (opaque session tokens, `httpOnly` + `Secure` + `SameSite=Lax` cookies, sessions persisted in Postgres with a Valkey read-through cache, Argon2id password hashing).
**Alternatives:** Lucia (**deprecated March 2025** — the npm package is now explicitly a "learning resource, not a library," so it cannot be a dependency), Auth.js/NextAuth (in security-only maintenance mode, and — more importantly — it's a _Next.js_-shaped solution; putting auth in Next.js would contradict the brief's requirement that NestJS is the single source of truth, since `admin` and any future client would then depend on the storefront's auth), Passport.js strategies inside Nest (viable but adds an abstraction layer for a fairly simple session model; revisit if OAuth/social login is added).
**WhyःNestJS owns auth:** consistent with "NestJS is the source of truth" for every other domain — the storefront and admin are just authenticated HTTP clients of the API, never independent auth authorities.
**Consequences:** MFA-readiness = TOTP secret column on `User`, unused until MFA ships; RBAC via `Role`/`Permission` tables (`DATABASE.md`, `SECURITY.md`).
**Note:** login/logout/session issuance are now implemented on top of this design (`AuthController`/`AuthService`, DECISIONS.md ADR-032) — the admin API is reachable by a real client. Registration and password-reset HTTP endpoints remain unbuilt, tracked separately (ADR-032).

## ADR-022: Shipping — provider-agnostic `ShippingProvider` abstraction, carrier deferred ✅ — confirmed 2026-09-08

**Decision:** `apps/api`'s order/fulfillment domain depends only on a `ShippingProvider` interface — never on a specific carrier SDK. For v1 this is implemented as a `ManualShippingProvider`: no external carrier API calls, no live rate-shopping, no automated label generation, no tracking webhooks. Admin marks an order ready-to-ship/shipped manually and enters a free-text carrier name/tracking number on the `Shipment` record. `ShippingMethod` (the customer-facing option — e.g. "Standard", "Express") stays carrier-agnostic: name, translated label, price, estimated delivery window — **no carrier-specific fields, no enum of carrier names, anywhere in the schema.**

```ts
// Illustrative shape only — not implemented in this phase.
interface ShippingProvider {
  quoteRates(destination: AddressSnapshot, parcel: ParcelSnapshot): Promise<ShippingRateOption[]>;
  createShipment(order: OrderSnapshot, method: ShippingMethodRef): Promise<ShipmentRef>;
  getTrackingStatus(shipmentId: string): Promise<TrackingStatus>;
  cancelShipment(shipmentId: string): Promise<void>;
}
```

```
ShippingProvider
└── ManualShippingProvider     # v1 — no carrier API; admin enters tracking info manually
    (PostNordShippingProvider / DHLShippingProvider / BringShippingProvider
     — or another carrier's adapter — added later behind the same interface,
     once a carrier is selected; none is chosen now)
```

**Why:** you've explicitly deferred the carrier decision (PostNord/DHL/Bring/other) and asked for the same non-coupling discipline already applied to payments (ADR-014) — the domain model must not hardcode a carrier, and adding a real carrier later must not require redesigning orders, checkout, inventory, or payment architecture.
**Alternatives considered:** provisionally integrating one carrier now (rejected — you explicitly ruled this out, and it's exactly the speculative work the brief warns against); a typed enum on `Shipment` with a single `MANUAL` value pre-reserving future carrier values (rejected in favor of free text for v1 — an enum implies pre-deciding future values; free text is genuinely non-committal and trivially migrated to a typed/foreign-keyed carrier reference once one is chosen).
**Consequences:**

- `ShippingMethod` and `Shipment` (`DATABASE.md` §1) carry zero carrier-specific columns in v1; `Shipment.carrierName`/`Shipment.trackingNumber` are free-text/nullable, not foreign keys into a carrier table.
- `apps/api` gets a `shipping` domain module (`ARCHITECTURE.md` §3) analogous to `payments`, hosting the `ShippingProvider` interface and the `ManualShippingProvider` implementation.
- When a carrier is selected, its adapter (e.g. `PostNordShippingProvider`) implements the same interface and is swapped in via configuration — order/checkout/inventory/payment code is untouched, mirroring how `PaymentProvider` isolates Stripe.
- **Not a Phase 1 blocking decision** — `ManualShippingProvider` is trivial enough to include in the Phase 1 schema/scaffold without waiting on a carrier choice.

## ADR-023: Repository-wide ESM import convention ✅ — confirmed 2026-09-08

**Context:** `node dist/main.js` failed with `ERR_MODULE_NOT_FOUND` because `packages/config`'s source used `.js`-suffixed relative imports (`./env.js`) pointing at files that only exist as `.ts` (the package has no build step). TypeScript's NodeNext resolution silently remaps a `.js` specifier to a sibling `.ts` file **at compile/typecheck time only** — Node's own runtime ESM resolver has no such remapping. The same latent bug existed in `packages/validation` too (not yet triggered, since nothing imported it at runtime yet) — fixed as part of resolving this completely rather than patching only the file that happened to fail.

**Decision — a two-tier convention, chosen by whether the package/app has its own build step:**

1. **Apps/packages that compile to `dist/`** (`apps/api`; later `apps/storefront`/`apps/admin` via Next.js's own build) — relative imports use **`.js` extensions**, the standard TypeScript NodeNext convention. At compile time TS resolves `./foo.js` against the sibling `./foo.ts`; after compilation, the same `.js` specifier correctly points at the real compiled sibling `.js` file sitting next to it in `dist/`. No special flags needed for the package's own files.
2. **Source-only internal workspace packages with no build step** (`packages/config`, `packages/types`, `packages/validation`, `packages/database` — each consumed directly via `"main": "./src/…ts"`, deliberately never compiled) — relative imports use **literal `.ts` extensions**, exactly matching the convention Prisma's own generated client already uses internally. Each such package's `tsconfig.json` sets `allowImportingTsExtensions: true`. This lets Node 24's stable native type-stripping resolve these files directly at runtime, with zero build step, bundler, or ts-node/tsx.

A consuming build (`apps/api`) that type-checks or compiles against a tier-2 dependency's source also needs `allowImportingTsExtensions: true` itself (to parse those `.ts`-suffixed specifiers), and its `tsconfig.build.json` (the config `nest build` actually emits from) additionally needs `rewriteRelativeImportExtensions: true`, which TypeScript requires as a companion to `allowImportingTsExtensions` whenever emitting (not `noEmit`) — `apps/api/tsconfig.json` and `apps/api/tsconfig.build.json` are the reference implementation of this reconciliation.

**Why this is correct, not a workaround:** the two tiers aren't an arbitrary per-file choice — they're the necessary consequence of TypeScript's `.js`→`.ts` remapping being compile-time-only, colliding with two genuinely different consumption models. A package that gets compiled needs `.js` specifiers, because after compilation that's what's really sitting on disk. A package consumed as raw source needs `.ts` specifiers, because that's what's really sitting on disk. Mixing the two within a no-build-step package is exactly what broke.

**Verified (not asserted):** `node --input-type=module -e "import('@ame-de-fil/validation')…"` resolves cleanly and its schemas execute correctly (including the ADR-021 `fr-FR`-rejection behavior) — proving tier 2 works end-to-end, not just for the one file that originally failed. `nest build` → `node dist/main.js` boots all 14 modules, serves `/health` and `/api/docs-json` correctly. `dist/` contains only `apps/api`'s own compiled output — `packages/*` are resolved live via `node_modules` at runtime, never bundled or duplicated into it.

**Consequences:** every future source-only workspace package follows tier 2 from the start — _when its consumers resolve modules via raw Node ESM_ (see the correction below for the other case).

**Correction (Phase 1 storefront/admin checkpoint):** the line above was wrong for `packages/ui`. The real dividing line isn't "has a build step" — it's **how the package is actually resolved at the point of use**:

- **Tier 1 — compiled, consumed via raw Node** (`apps/api`): `.js`-suffixed relative imports (standard NodeNext).
- **Tier 2 — source-only, consumed via raw Node** (`packages/config`, `packages/types`, `packages/validation`, `packages/database`): literal `.ts`-suffixed relative imports + `allowImportingTsExtensions: true`, extending the shared NodeNext base as-is.
- **Tier 3 — source-only, consumed only via a bundler** (`packages/ui`, consumed exclusively by `apps/storefront`/`apps/admin`'s Turbopack/webpack build, never by raw Node): **extensionless** relative imports, with the package's own `tsconfig.json` overriding the shared base to `"moduleResolution": "bundler"`, `"module": "ESNext"`. Discovered because `next/link`'s package exports aren't structured for NodeNext's stricter resolution — a real, reproducible `TS2307` typecheck failure, not a style preference. "Bundler" is the resolution mode Next.js itself is built around; forcing NodeNext onto a Next.js-only-consumed package fights the tool it exists to serve.

The apps themselves (`apps/storefront`, `apps/admin`) also use `moduleResolution: "bundler"`, matching Next.js's own generated tsconfig convention, not `apps/api`'s NodeNext setup — apps/api is the one raw-Node-executed app in this monorepo; everything else that runs through a bundler follows tier 3's convention instead.

## ADR-024: Stripe payment integration — implementation decisions ✅

**Decision:** `StripePaymentProvider implements PaymentProvider` (`apps/api/src/payments/`), card payments only, **automatic capture**. `PaymentsModule` binds `PAYMENT_PROVIDER` via a `useFactory` selecting `StripePaymentProvider` when `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` are both set, `PendingPaymentProvider` otherwise — no Stripe test credentials were available in this checkpoint's environment, so this fallback is what boots/tests/builds actually exercised here.

**Klarna/Swish:** not wired in this checkpoint despite ADR-014 routing them through the same Stripe integration eventually — v1 scope here is card only. `StripePaymentProvider`'s `automatic_payment_methods: { enabled: true }` would surface them automatically once Stripe account settings enable those methods, but that's untested and not claimed as working.

**Transaction boundary — kept exactly as designed, not redesigned:** `StripePaymentProvider.createPayment` runs inside `CheckoutService`'s existing single checkout transaction (`PaymentProvider.createPayment(tx, ...)`'s signature already required this). **Accepted risk:** a DB transaction failure after a successful Stripe call can orphan an uncharged `PENDING` PaymentIntent with no local `Order`/`Payment` row. Mitigated for the one realistic repeat-call case (`CheckoutService`'s own `orderNumber`-collision retry) via a Stripe request-level `idempotencyKey` derived from the order ID; not otherwise solved — flagged as future reconciliation-job scope (`PAYMENTS.md` §5), not built now. Rejected alternative: splitting the transaction to create the PaymentIntent outside the lock-holding window — would meaningfully reduce lock time but reintroduces a TOCTOU gap between cart/stock re-validation and order creation that the current single-transaction design specifically avoids; revisit only if load testing (`ROADMAP.md` Phase 7) shows this path actually contends under load.

**Webhook processing is synchronous**, not handed to a BullMQ job as `PAYMENTS.md` §5 originally specified — there is no BullMQ/queue infrastructure anywhere in this repo. Disclosed rather than silently deviating. (The reservation-expiry scheduler was in the same category as of this ADR entry's original writing — resolved separately, see ADR-025.)

**Guest order-status polling token** (`OrderStatusToken` — new Prisma model, `packages/database/prisma/migrations/20260909000000_add_order_status_token/`): 256-bit random token (`randomBytes(32)`, base64url), returned once in the checkout response, stored server-side only as a SHA-256 hash — a deliberate divergence from `Session.id`'s plaintext-token-as-primary-key convention (ADR-015), justified because this token travels in a request header set by client-side JS and is handed to the customer in a JSON body, not an httpOnly cookie the browser itself never exposes. Scoped one-per-order, time-limited (`ORDER_STATUS_TOKEN_TTL_HOURS`, default 2h) but reusable within that window. Transported as a custom header (`X-Order-Status-Token`), never a query parameter, to avoid it landing in access logs. This is the one schema addition this checkpoint required — everything else needed for Stripe (Payment/PaymentAttempt/WebhookEvent/IdempotencyKey/StockReservation/InventoryItem/InventoryMovement) already existed from the Phase 1 schema.

**CSP for Stripe.js** added to `apps/storefront/next.config.ts` (there was no prior baseline) — `script-src`/`style-src` include `'unsafe-inline'`, verified necessary live (Next.js's own inline hydration/RSC bootstrap scripts are unnonced; omitting this broke the app's own JS, not just a theoretical gap) rather than assumed. A nonce-based CSP would avoid this but requires per-request middleware plumbing out of scope for this checkpoint.

**Verified (not asserted) in this environment:** `pnpm lint`, `pnpm typecheck`, `pnpm test` (252 API tests + 9 validation tests, all mocking Stripe — no real credentials touched), and `pnpm build` (API + storefront + admin) all pass with no `STRIPE_*` credentials configured, confirming the `PendingPaymentProvider` fallback path is real, not aspirational. No live Stripe test-mode verification was performed — no Stripe test credentials were available in this environment; also no live Postgres/Docker was available, so the API could not be run against a real database at all (checked directly: `apps/api` boots cleanly and correctly reports `/health` as degraded with `database: down`, consistent with `DEPLOYMENT.md` §1's already-disclosed Docker/WSL gap). Full checkout-with-real-payment E2E verification remains pending external verification, not claimed here.

## ADR-025: Reservation-expiry scheduling — `@nestjs/schedule` in-process interval, not BullMQ ✅

**Context:** `ReservationExpiryService.releaseExpiredReservations()` (the idempotent release logic itself) existed from the Stripe checkpoint (ADR-024) with no automatic trigger — only a manual `POST /admin/checkout/expire-reservations` endpoint. `ARCHITECTURE.md` §5 and `DATABASE.md` §4 originally described the intended trigger as a BullMQ delayed job, matching ADR-013's broader plan for background processing.

**Decision:** `ReservationExpiryScheduler` (`apps/api/src/checkout/reservation-expiry.scheduler.ts`) — a periodic sweep using `@nestjs/schedule`'s `SchedulerRegistry`, registering a plain `setInterval` at boot (`onModuleInit`) rather than a static `@Interval()` decorator, specifically so the interval itself stays a configurable env var (`RESERVATION_EXPIRY_SWEEP_INTERVAL_MS`, default 60s) — a decorator argument is a compile-time constant and can't read `ConfigService`. Every tick calls the existing, unmodified `ReservationExpiryService.releaseExpiredReservations()`, which queries for *all* currently-expired reservations (not one job per reservation's `expiresAt`, as the original per-item BullMQ-job sketch implied).

**Why not BullMQ, as ADR-013 originally specified for this job:** BullMQ requires Valkey as its backing store, and — like PostgreSQL in this dev environment — no Valkey instance is provisioned or reachable here either. Building the BullMQ integration now would mean shipping code that has never actually run, for a job whose correctness requirement (release stock that's provably expired, idempotently, on a bounded delay) doesn't need BullMQ's retry/backoff/dead-letter guarantees — a periodic idempotent sweep is a complete, correct solution on its own. `@nestjs/schedule` has no such external dependency and its peer range (`^11.0.0 || ^12.0.0`) covers this project's Nest 12, verified against npm before adding (the same check that previously ruled out `@nestjs/throttler` for this Nest version — `SECURITY.md` §4).

**Consequences:**

- `ARCHITECTURE.md` §5, `DATABASE.md` §4, and `PAYMENTS.md` §7 are corrected to describe this mechanism, not the originally-sketched BullMQ job — reservation expiry is now the one background job in this project that's actually implemented and running, distinct from the still-unbuilt BullMQ jobs (webhook-retry backoff, low-stock digests, transactional email) ADR-013 covers.
- Runs correctly under horizontal scaling with no coordination needed: each API instance registers its own independent interval, but `ReservationExpiryService`'s existing guarded `PENDING -> EXPIRED` conditional updates mean only one instance's sweep ever actually claims and releases a given reservation — redundant sweeps across instances cost an extra query, never a double-release.
- **Not equivalent to BullMQ on every dimension** — an in-process `setInterval` has no persistence across a process restart (a reservation that expired in the seconds before a restart just waits for the next tick after boot, which is still bounded by the sweep interval, not lost or silently skipped) and no delivery/retry guarantees beyond "try again next tick," which the idempotent design tolerates but a true BullMQ job's dead-letter queue would additionally make observable. Acceptable for v1; revisit if a real BullMQ/Valkey deployment exists and operational visibility into missed sweeps becomes a real requirement.
- The manual `POST /admin/checkout/expire-reservations` endpoint (`AdminCheckoutController`) is retained as the ops-triggered complement for an immediate on-demand run, not superseded by the scheduler.
- **Verified (not asserted):** `pnpm lint`/`typecheck`/`test` (257 API tests, 5 new — covering interval registration with the configured value, tick-driven calls to `releaseExpiredReservations` under fake timers, error-swallowing on a failed tick without killing the interval, and interval cleanup on module destroy) and `pnpm build` all pass. `apps/api` boots cleanly with `ScheduleModule.forRoot()` and the scheduler registered — checked directly via a live boot in this environment (still against no reachable database, so the sweep's actual DB behavior at the configured 60s interval was not observed end-to-end; the release logic itself was already verified in `reservation-expiry.service.spec.ts` from the earlier checkpoint).

## ADR-026: Reservation-expiry vs. payment-success race — Order state on late success ✅

**Context:** `ReservationExpiryScheduler`/`ReservationExpiryService` (ADR-025) and `PaymentsWebhookService`'s `payment_intent.succeeded` handler (ADR-024) both act on the same `Order`/`StockReservation` rows independently and asynchronously — the sweep on a fixed interval, the webhook whenever Stripe's customer-facing payment confirmation actually completes. This checkpoint had, for the first time, a reachable local Postgres (`docker-compose.yml`) and real Stripe test-mode credentials, and used them to run the full checkout → PaymentIntent → webhook → state-transition flow live — surfacing and fixing two other real defects invisible under mocked tests first (a Prisma create-payload/schema field mismatch in `checkout.service.ts`, and the P2002-duplicate-key detection helper in `prisma-errors.ts` being written against the classic query-engine's error shape rather than the `@prisma/adapter-pg` shape this project actually runs — ADR-009), before this race was even reachable to test.

With those fixed, live testing reproduced a real, reachable race: a reservation's TTL can expire while its `PaymentIntent` is still `PENDING` (a slow customer, a 3DS delay), and the sweep can commit `Order.status → CANCELED` *before* the later `payment_intent.succeeded` webhook arrives for that same order. `PaymentsWebhookService.confirmOrderOrFlagStockLost`'s stock-lost branch (`DATABASE.md` §4 step 3) originally guarded only on `status = PENDING_PAYMENT`, so whichever side of the race the sweep won, the intended `PAYMENT_SUCCEEDED_STOCK_LOST` write matched zero rows and silently did nothing — leaving `Payment.status = PAID` under `Order.status = CANCELED` forever. That is exactly the "silently keep the money for nothing" outcome `PAYMENTS.md` §4's stock-lost design exists to prevent, just reached via a path the original guard didn't cover.

**Decision:** broaden that guard to `status IN (PENDING_PAYMENT, CANCELED)`, and clear `canceledAt` on the transition (the order didn't actually end up canceled). No schema change, no migration — a guard-condition fix. This is safe without a cancellation-reason column because, in the current implementation, `CANCELED` has exactly two sources: this same sweep, and `handleFailedOrCanceled` for a *definitive* Stripe failure/cancellation on the *same* PaymentIntent. The second source can never reach this branch for a later `succeeded` event on that PaymentIntent — `handleSucceeded`'s own, earlier `Payment.status = PENDING` guard already rejects it, since a failed/canceled webhook already moved `Payment.status` away from `PENDING`. So an order found `CANCELED` in this branch can only be this exact race, never a different cancellation being incorrectly reopened by an unrelated event. Full narrative in `PAYMENTS.md` §4a.

**Consequences:**

- `PAYMENTS.md` §3's order state-machine diagram gains two edges (`PENDING_PAYMENT → PAYMENT_SUCCEEDED_STOCK_LOST`, `CANCELED → PAYMENT_SUCCEEDED_STOCK_LOST`) that were previously undiagrammed even though `PAYMENT_SUCCEEDED_STOCK_LOST` itself has existed as an `OrderStatus` value since ADR-024.
- **Correction to ADR-024's "no live verification was performed" note:** that was an accurate record of that checkpoint's environment at the time. This checkpoint's live verification covers the successful/failed/canceled payment paths, server-authoritative amounts, webhook signature verification and rejection, replay idempotency (including under genuine concurrent duplicate delivery, not just sequential replay), guest order-status token authorization, the reservation-expiry scheduler running live, and this race — all against a real database and real Stripe test API.
- Regression test added directly against the guard in `payments-webhook.service.spec.ts`.
- **Verified (not asserted):** reproduced live — reservation force-expired, the running scheduler's own tick canceled the order, the PaymentIntent was then confirmed via the real Stripe API, the real signature-verified webhook was processed, and the order landed on `PAYMENT_SUCCEEDED_STOCK_LOST` with `Payment.status = PAID`, `canceledAt` cleared, the reservation left `EXPIRED` (not consumed), and zero inventory movement. `pnpm --filter @ame-de-fil/api test`, workspace-wide `pnpm lint`/`pnpm typecheck`/`pnpm test`, and `pnpm build` all pass.

## ADR-029: Admin fulfillment — `CONFIRMED → READY_TO_SHIP → SHIPPED → DELIVERED` ✅

**Context:** ROADMAP.md Phase 4 lists "shipment tracking via `ManualShippingProvider` (admin-entered, carrier-agnostic — ADR-022)" as a distinct item from "made-to-order production-time flow" and from Phase 5's "order management" admin UI. ADR-022 already fully decided the architecture (no carrier API, admin manually enters free-text carrier name/tracking number); `orders.module.ts`'s own prior comment named this gap explicitly: *"full order lifecycle (detail views, admin fulfillment, refunds) is still a later phase."* This checkpoint builds that admin-fulfillment piece.

**Decision:** three new admin endpoints under `apps/api/src/orders/admin-orders.controller.ts` (`AdminOrdersService`), gated by a new `orders.fulfill` permission (consistent with the existing `checkout.manage`/`inventory.adjust`/`products.create` convention — no seed data added, since no `Permission`/`RolePermission` rows are seeded anywhere in this project yet for *any* permission string, a pre-existing, project-wide gap):

- `POST /admin/orders/:orderId/ready-to-ship` — `CONFIRMED → READY_TO_SHIP`.
- `POST /admin/orders/:orderId/ship` — `READY_TO_SHIP → SHIPPED`, creates a `Shipment` row (`carrierName`/`trackingNumber`/`trackingUrl`, all optional free text per ADR-022) with `shippedAt`.
- `POST /admin/orders/:orderId/deliver` — `SHIPPED → DELIVERED`, updates that `Shipment` to `DELIVERED`/`deliveredAt`.

Each is a guarded conditional `updateMany` (`WHERE status = <expected>`) — the same idiom as `ReservationExpiryService`/`PaymentsWebhookService` — but unlike those two, a zero-row match **throws** (`409 ConflictException`) rather than silently no-opping: those exist to tolerate retried webhook/sweep deliveries, whereas a manual admin action invoked against the wrong order state is a real mistake that should surface as an error (`TESTING.md` §2: "illegal transitions must throw"). `Shipment` is `create`d, not `upsert`ed — `Shipment.orderId` is a plain indexed FK, not `@unique` (the schema already allows multiple `Shipment` rows per order for a future partial-shipment case), so there's no unique key an upsert could target; v1's manual flow only ever produces one per order.

**Deliberately deferred, disclosed rather than silently absent:**
- The `IN_PRODUCTION` branch and `productionTimeDays` tracking for made-to-order items — `CONFIRMED → READY_TO_SHIP` applies uniformly today regardless of made-to-order mix. That's the separate, not-yet-started "made-to-order production-time flow" roadmap item; building it here would be scope creep beyond what was asked.
- Any admin frontend — `apps/admin` has no order pages at all yet (`orders/page.tsx` is a `ComingSoon` placeholder), and "Orders (detail, ...)" is explicitly `PRODUCT_SPEC.md` §5 / `ROADMAP.md` Phase 5 scope. This checkpoint is the backend capability that UI will call.
- Customer-facing shipment visibility (tracking info in the guest order-status response, or a shipping-notification email) — `orderStatusResponseSchema` stays deliberately minimal (`DECISIONS.md` ADR-024) and is not touched; a shipping-notification email is Phase 4's separate "transactional email" item.

**Consequences:**
- No schema migration — `Shipment`/`OrderStatus`/`ShipmentStatus` already existed exactly as needed.
- `PAYMENTS.md` §3 gets a short implementation note naming the new endpoints and the disclosed `IN_PRODUCTION` deferral (no diagram change — the diagram already showed this exact chain).
- **Verified (not asserted):** new unit tests (`admin-orders.service.spec.ts`, `admin-orders.controller.spec.ts` — the latter through the real `SessionAuthGuard`/`PermissionsGuard`/`CsrfGuard` chain, mirroring `inventory.controller.spec.ts`) and a new Testcontainers integration test (`admin-orders.integration.spec.ts`) walking a real order through the full chain against real Postgres, plus the two illegal-transition-rejects cases. `pnpm --filter @ame-de-fil/api test` (286 tests, 17 new) and `test:integration` (8 tests, 3 new) pass. Live smoke-tested against the running local API with a real admin session: the full `ready-to-ship → ship → deliver` chain, and confirmed a premature `ship` call on a still-`CONFIRMED` order correctly rejects with `409`.

Live against the real local Postgres and Stripe test API: a real made-to-order checkout snapshotted `madeToOrder`/`productionTimeDaysSnapshot` correctly at checkout time, its real webhook landed the order on `IN_PRODUCTION` (not `CONFIRMED`) with zero inventory movement, `markReadyToShip` succeeded from `IN_PRODUCTION` via a real admin session, and a separate ready-to-ship-only checkout was re-run as a regression check, still landing on `CONFIRMED`.

## ADR-031: Transactional email — generic SMTP/Mailpit, dispatched synchronously post-commit ✅

**Context:** `ROADMAP.md` Phase 4 named transactional email (order confirmation, shipping notification) as its last unbuilt item; `ARCHITECTURE.md` already reserved `packages/email` and a `notifications` domain module for it, and `docs/SECURITY.md` §10 already flagged "the email provider" as a third-party processor needing a DPA "tracked at implementation/vendor-selection time, not now." Vendor selection itself remains explicitly out of scope here (ADR-020's deferred group), same as deployment target and image storage — this checkpoint builds the dispatch mechanism and the two templates, not a choice of Postfix/SES/Postmark/Resend/etc.

**Decision:**

1. **`packages/email`** — React Email (`@react-email/components`, `@react-email/render`) templates (`OrderConfirmationEmail`, `ShippingNotificationEmail`), bilingual `sv-SE`/`en` via a plain `locale` prop switched on directly (next-intl isn't reachable outside Next.js — the same idiom `checkout-cart.ts`'s `resolveVariantLabel` already uses for this exact problem), money formatted inline via `Intl.NumberFormat` (no new shared formatting package — nothing here needs one beyond what `Intl` already gives for free). Only `renderOrderConfirmationEmail`/`renderShippingNotificationEmail` are exported (`RenderedEmail = { subject, html, text }`) — the templates themselves stay internal, matching `packages/validation`'s Tier 2 shape (DECISIONS.md ADR-023) exactly, **with no JSX at all.** JSX/`.tsx` was tried first and reverted: Node's native type-stripping (the mechanism ADR-023 itself names as what makes Tier 2 packages runnable with zero build step) only erases type annotations — it has no JSX transform, so a `.tsx` file throws `ERR_UNKNOWN_FILE_EXTENSION` the instant `apps/api` actually imports it at runtime, a failure `tsc --noEmit` can't catch since typechecking doesn't exercise Node's module loader at all. The templates are written instead as plain `.ts` using `React.createElement` directly via a small local wrapper (`src/h.ts`) — functionally identical output (JSX is sugar for exactly these calls), verified by actually booting the compiled `apps/api` and rendering both templates, not just by a passing typecheck. This is the first time this project's Tier 2 convention has met a package that would naturally want JSX, and the resolution is "don't write JSX in a Tier 2 package," not a new tier — `apps/api`'s own `tsconfig.json` needed no change.
2. **`apps/api/src/notifications`** — `EmailProvider` (`send({ to, subject, html, text })`) is a provider-agnostic boundary, the same pattern as `PaymentProvider`/`ShippingProvider` (ADR-014/ADR-022): `SmtpEmailProvider` (generic `nodemailer`, not a vendor SDK — any SMTP-speaking service, real vendor or Mailpit, works unchanged) and `PendingEmailProvider` (no send attempted; throws a specific, caught error) resolve via `NotificationsModule`'s `EMAIL_PROVIDER` factory exactly like `PaymentsModule`'s `PAYMENT_PROVIDER` factory — `SmtpEmailProvider` is never registered standalone, so Nest never eagerly constructs it (and never eagerly requires `SMTP_HOST`) when SMTP isn't configured. `NotificationsService.sendOrderConfirmation(orderId)`/`.sendShippingNotification(orderId)` each: check for an existing `SENT` `Notification` for that `(type, orderId)` pair and no-op if found; create a `PENDING` `Notification` row; render via `packages/email`; call `EmailProvider.send`; mark `SENT`/`FAILED`. Every public method is a catch-all — a render or send failure is caught, logged, and recorded as `FAILED`, **never rethrown**, so this can never fail its caller.
3. **Trigger points, both post-commit:** `PaymentsWebhookService.handle` now returns the confirmed `orderId` from its `$transaction` block (only non-null the one time `confirmOrderOrFlagStockLost` actually drives a `PENDING_PAYMENT -> CONFIRMED/IN_PRODUCTION` transition — never for the stock-lost branch, which needs manual admin resolution, not a customer-facing "confirmed" email) and calls `notifications.sendOrderConfirmation` only after that transaction has resolved. `AdminOrdersService.markShipped` calls `notifications.sendShippingNotification` immediately after its own transaction commits, before building the response. Neither call is inside the transaction it follows — an SMTP round-trip must never hold an Order/Shipment write's locks open, and `NotificationsService` never throwing means a slow or failed send can never roll back that write.
4. **`docker-compose.yml`** — `mailpit` (`axllent/mailpit:v1.31`, SMTP `1025`, web UI `8025`), matching `DEPLOYMENT.md`'s already-stated local stack ("Postgres, Valkey, SMTP catcher"). Valkey stays out, per ADR-012/ADR-025's existing precedent of not standing up infrastructure a feature doesn't actually need yet.
5. **`packages/config/src/env.ts`** — `SMTP_HOST`/`SMTP_PORT`/`SMTP_FROM`, all optional, `SMTP_HOST`/`SMTP_FROM` via the same `optionalSecret()` blank-placeholder normalization as `STRIPE_SECRET_KEY`. `SMTP_PORT` deliberately has no schema-level default — Mailpit listens on `1025`, not the standard `587`, so defaulting would silently point at the wrong port for the one SMTP server this project actually ships a config for; `SmtpEmailProvider` itself falls back to `587` only when `SMTP_HOST` is set but `SMTP_PORT` isn't.

**Idempotency and crash/retry behavior — disclosed, not overstated:** `NotificationsService`'s `wasAlreadySent` check (`Notification.findFirst` filtered on `type` + `status = SENT` + a JSON-path filter on `payload.orderId`, native GA Postgres JSON filtering, no preview flag) is a best-effort, **application-level** guard, not a database-enforced one — `Notification` carries no unique constraint on `(orderId, type)`, because payload is a free-form `Json` column with no dedicated `orderId` column to put one on, and adding a migration for that is out of scope here. Concretely, this means:

- A retried Stripe webhook delivery for an already-confirmed order never reaches the notification call at all — `handleSucceeded`'s own `PENDING`-payment guard and `confirmOrderOrFlagStockLost`'s own guarded update both already no-op on a second delivery, so `confirmedOrderId` stays `null` and `sendOrderConfirmation` is never even invoked. This is the realistic, actually-reachable case, and it's covered without needing the DB-level guard at all.
- The `wasAlreadySent` guard exists for the next case: something invokes `sendOrderConfirmation`/`sendShippingNotification` again for an order that already has a **successfully sent** notification of that type (e.g. a future retry mechanism, or a manual re-trigger). It is not a race-proof lock — two genuinely concurrent invocations could both pass the check before either writes its row — but no code path in this checkpoint produces genuine concurrent invocations for the same order, so this is a correctness net, not decoration.
- **What this explicitly does not solve:** a process crash between the triggering transaction's commit and the notification call completing loses that notification permanently — there is no queue, no outbox row written in the same transaction, and no retry sweep (BullMQ remains out of scope, ADR-013/ADR-025). A `FAILED` `Notification` row (from a real send failure, e.g. Mailpit down) is equally never automatically retried today; it's a durable record of the failure, not a retry guarantee. This is the same category of gap ADR-025 already accepted for reservation-expiry's `setInterval` sweep versus a real BullMQ job, and the same "disclosed rather than silently deviating" posture ADR-024 used for synchronous (non-BullMQ) webhook processing — a durable outbox/queue pattern is the correct fix if this gap ever needs closing, and is deliberately not built here.
- `notifications.integration.spec.ts` documents this directly against a real database: calling `sendOrderConfirmation` twice against `PendingEmailProvider` (which always fails) produces **two** `FAILED` rows, not one — proving the guard only ever short-circuits a repeat call after a genuine `SENT`, never after a `FAILED`.

**Consequences:**

- `docs/ARCHITECTURE.md` marks `packages/email` implemented (previously reserved-but-empty) and the "transactional email" bullet under the BullMQ-jobs list is corrected to describe this synchronous mechanism instead, the same kind of correction ADR-025 made for reservation expiry.
- `docs/ROADMAP.md` Phase 4 marks transactional email done; real vendor selection (and therefore real production sending, and the DPA `docs/SECURITY.md` §10 flags) remains explicitly deferred — Mailpit is a local dev catcher, not a vendor.
- New tests: `packages/email` (both templates, both locales, asserting order number/total/tracking number appear in the rendered output), `email-provider.spec.ts` (`SmtpEmailProvider` against a mocked `nodemailer`, `PendingEmailProvider` throwing), `notifications.service.spec.ts` (`Notification` created `PENDING`, resolved `SENT`/`FAILED`, the idempotency guard, missing-order/missing-email no-ops, never rethrowing), `notifications.integration.spec.ts` (real Postgres, `PendingEmailProvider` — no real SMTP container available inside Testcontainers/Vitest, so this proves the DB bookkeeping and trigger wiring, not actual mail delivery), and updates to `payments-webhook.service.spec.ts`/`admin-orders.service.spec.ts` asserting the notification call happens only after `$transaction` resolves (via `mock.invocationCallOrder`).
- **Verified (not asserted):** `pnpm --filter @ame-de-fil/api test` (303 tests, 15 new) and `test:integration` (14 tests, 3 new) pass, as do `pnpm --filter @ame-de-fil/email test`/`lint`/`typecheck` and workspace-wide `pnpm lint`/`pnpm typecheck`/`pnpm test`/`pnpm build`. `nest build` → `node dist/main.js` boots cleanly (including the new `NotificationsModule`, wired into both `PaymentsModule` and `OrdersModule`) against the real local Postgres, `/health` reports `database: up`. Live against that same real Postgres and a real Mailpit container (`docker compose up -d mailpit`): directly invoking the real, compiled `NotificationsService` (`SmtpEmailProvider`, `SMTP_HOST=localhost`/`SMTP_PORT=1025`) against a real seeded order produced a real order-confirmation email that actually arrived in Mailpit's API/web UI, with `Notification.status = SENT`; the same for a shipping notification against a real `Shipment` row. Stopping the Mailpit container and retrying against `SmtpEmailProvider` produced a genuine `ECONNREFUSED`, correctly recorded as `Notification.status = FAILED`, with the `Order` row completely unaffected either way. **Not verified live in this checkpoint:** the full real-checkout → Stripe-webhook → order-confirmation-email path end-to-end — no Stripe test-mode credentials were available in this environment (same gap noted for other checkpoints run without them). The webhook-side wiring itself (`confirmedOrderId` only propagating on a genuine transition, the call firing only after `$transaction` resolves) is covered by `payments-webhook.service.spec.ts`'s mocked-Prisma assertions and `reservation-expiry-race.integration.spec.ts`'s real-Postgres run, just not by a real Stripe delivery.

## ADR-032: Real auth entry point — `AuthController`/`AuthService` on top of the existing session design ✅

**Context:** the ADR-031 checkpoint's documentation audit found that no login/registration/logout HTTP endpoint existed anywhere — `SessionService`/`PasswordService` (ADR-015) were session/password *building blocks* with no HTTP surface, so every admin-only route shipped since Phase 2 (`admin/products`, `admin/inventory`, `admin/checkout`, `admin/orders`) was unreachable by a real client, only callable in tests that seed a `Session` row directly. `ROADMAP.md` Phase 4 was updated to name this explicitly. This checkpoint closes it, without touching `SessionService`/`PasswordService`/`SessionAuthGuard`/`PermissionsGuard`/`CsrfGuard` at all — they were already correct; nothing existed to call them.

**Decision:**

1. **API surface** — `apps/api/src/identity/auth.controller.ts` (`AuthController`) + `auth.service.ts` (`AuthService`), added to the existing `IdentityModule`:
   - `POST /auth/login` — `@Public()` (no session exists yet to require one), `@RateLimit({ windowMs: 60_000, max: 5 })` per SECURITY.md §4's explicit list. Verifies email/password against `User.passwordHash` (`PasswordService`, unchanged), then calls `SessionService.createSession` (unchanged) and `SessionService.validateSession` (unchanged, reused rather than re-deriving the roles → permissions flattening query a second time) to build the response.
   - `POST /auth/logout` — no `@Public()`/`@OptionalAuth()`, the ordinary default-deny posture: requires a valid session **and** a correct `X-CSRF-Token` header (`CsrfGuard`, unchanged, applies in full here). Calls `SessionService.revokeSession` (unchanged).
   - `GET /auth/session` — `@OptionalAuth()`: `{ authenticated: false }` for no cookie at all, the caller's safe user + permissions for a valid one, and `SessionAuthGuard`'s existing hard-401 for a present-but-invalid cookie (deliberately not folded into `{ authenticated: false }` — that guard's own comment already explains why a stale/forged cookie is a different situation from no cookie).
   - No registration or password-reset endpoint — out of scope here by the checkpoint's own instruction, and identified separately rather than silently expanded into. There is currently no way to create a `User` row at all outside a direct DB insert or the test fixtures below.
2. **Cookies** — on login, sets both `SESSION_COOKIE_NAME` (`httpOnly`, `SameSite=Lax`, `Secure` when `NODE_ENV=production`, matching `cart-identity.ts`'s existing pattern exactly) and, newly, `CSRF_COOKIE_NAME` (**not** `httpOnly` — SECURITY.md §3's double-submit token is deliberately non-secret, only unguessable and session-bound, so it must be JS-readable to be echoed back as `X-CSRF-Token`). `CSRF_COOKIE_NAME` existed in `packages/config/src/env.ts` since Phase 1 but was never actually set anywhere until now. The CSRF token is also returned in the login/session JSON bodies, not only the cookie — a server-side (SSR) caller can't read a browser cookie at all, so the response body is the one delivery path guaranteed to work regardless of how a client's HTTP layer handles cookies. `POST /auth/logout` clears both via `response.clearCookie`.
3. **Timing-safe generic errors** — nonexistent email, wrong password, and a `DISABLED` account all throw the identical `401 { error: "InvalidCredentials" }`, and a nonexistent email still runs a real Argon2id verify against a memoized dummy hash (computed once via the real `PasswordService.hash`, not hand-crafted) rather than short-circuiting — SECURITY.md §1's "never reveal whether the email exists" covers the response body; a real latency gap between "no such user" (no hashing at all) and "wrong password" (one real Argon2id verify, deliberately slow) is the same leak via a side channel instead. `lastLoginAt` (an existing, previously-unused `User` column) is set on success.
4. **Log redaction (`app.module.ts`)** — pino-http's default serializers log request/response headers verbatim; `req.headers.cookie`, `req.headers["x-csrf-token"]`, and `res.headers["set-cookie"]` are now redacted (`remove: true`). This bug was **live-caught, not designed in from a checklist**: a real login → logout walkthrough against the running compiled API showed the real CSRF token sitting in a log line in plaintext on the first pass (the initial redact config only covered `cookie`/`set-cookie`, missing the CSRF value's own custom header) — fixed and re-verified against a second live run showing zero occurrences of either token value anywhere in the log.

**Alternatives considered:** folding the CSRF token delivery into the cookie alone (rejected — breaks any server-side caller, per point 2 above); a distinct error message for a disabled account (rejected — SECURITY.md §1 directly rules this out, it's the same account-existence leak as revealing "no such user" vs "wrong password").

**Consequences:**

- `docs/ROADMAP.md` Phase 4 marks the auth entry point implemented; `DECISIONS.md` ADR-015's note (added in the ADR-031 audit) is updated from "no endpoint exists" to "now implemented, see ADR-032" — the legend's own example of a disclosed ADR-015 gap is removed since the gap it pointed at is closed.
- Registration/password-reset, MFA, and any admin UI remain explicitly unbuilt — this checkpoint is the entry point only, not broader RBAC/user administration (Phase 5, untouched).
- `RateLimitGuard` remains per-IP only (its own pre-existing, disclosed limitation) — login is not additionally throttled per-account; this is unchanged, not introduced here.
- New tests: `auth.service.spec.ts` (unit, mocked Prisma/Password/Session — valid login, wrong password, nonexistent email, disabled account, identical error shape across all three, dummy-hash memoization, `lastLoginAt` update, safe-user shape never carries `passwordHash`), `auth.controller.spec.ts` (real Nest app + Supertest + the real guard chain, mocked `AuthService`/`SessionService` — cookie attributes, 400/401/403/429 paths, and a dedicated section proving the *pre-existing, unmodified* `InventoryController`+`PermissionsGuard` grants/denies access correctly against a session shaped like `AuthController` actually issues one), and `auth.integration.spec.ts` (Testcontainers, real Postgres, real `AuthService`/`SessionService`/`PasswordService` against a new `seedUserWithPermissions` fixture — the real `Role`/`Permission`/`UserRole`/`RolePermission` join `TESTING.md` §3 named as a target but never had a login path to reach until now).
- **Verified (not asserted):** `pnpm --filter @ame-de-fil/api test` (327 tests, 24 new) and `test:integration` (20 tests, 6 new) pass, as do workspace-wide `pnpm lint`/`pnpm typecheck`/`pnpm test`/`pnpm build`, and `nest build` → generating the OpenAPI document (`export-openapi.js`) succeeds with the three new `/auth/*` paths present, including the `GET /auth/session` discriminated-union response schema resolving correctly. Live, real HTTP walkthrough against the compiled API and the real local Postgres (a throwaway test admin user seeded directly via Prisma, since no registration endpoint exists, and removed afterward): anonymous `GET /auth/session` → `{ authenticated: false }`; login with correct credentials → `200` with both cookies set (`HttpOnly`/`SameSite=Lax` on the session cookie, readable on the CSRF one, `Secure` added when `NODE_ENV=production`) and a body with no `passwordHash`; authenticated `GET /auth/session` → the real user + permissions; a real, unmodified `GET /admin/inventory` → `200` with the granted `inventory.view` permission and `403` with an empty permission set, `401` with no cookie at all; `POST /auth/logout` → `403` without the CSRF header, `204` with it, both cookies cleared; the exact old session token resent explicitly afterward → `401 "Invalid or expired session"`, confirming server-side revocation rather than only client-side cookie clearing. This same walkthrough is what caught the log-redaction gap in point 4 above.

## ADR-033: Google sign-in — Authorization Code + PKCE, auto-registration on first sign-in ✅

**Context:** an optional, separately-scoped checkpoint on top of ADR-032's real auth entry point. No prior product/architecture decision existed for this beyond a one-line footnote in ADR-015 ("Passport.js... revisit if OAuth/social login is added"). Three scope questions were resolved with you before writing any code, since each materially changes the size and security posture of the feature: **storefront customers** (not admin staff — Google consumer OAuth isn't how staff accounts are normally provisioned), **auto-create a new account on first sign-in** (what "Sign in with Google" means for a real customer — this is the one case where AuthController creates a `User` with no password, distinct from ADR-032's password path which never does), and **stub/fallback only** — no real Google Cloud OAuth client was available in this environment, so nothing here has been verified against Google's actual servers, only against a real database and mocked Google responses.

**Decision:**

1. **Schema** (`DATABASE.md` §9) — one additive migration, `20260909205338_add_oauth_account`, generated for real via `prisma migrate dev` against the real local Postgres: `User.passwordHash` becomes nullable, and a new `OAuthAccount` model (`provider`, `providerAccountId` — Google's `sub` claim, never the email — `@@unique([provider, providerAccountId])`) links one or more external identities to a `User`. A dedicated table, not a `googleId` column on `User`, mirroring `Session`/`OrderStatusToken`'s existing precedent. `AuthService.login`'s pre-existing `user?.passwordHash ?? <dummy hash>` fallback (ADR-032) already treats `null` exactly like a nonexistent user with zero code changes — a Google-only account attempting password login gets the identical generic `InvalidCredentials` a wrong password would.
2. **`GoogleOAuthProvider`** (`apps/api/src/identity/google-oauth.provider.ts`) — the same provider-abstraction pattern as `PaymentProvider`/`EmailProvider` (ADR-014/ADR-031): `GoogleOAuthClient` (plain `fetch` calls against Google's own authorize/token/userinfo REST endpoints — no `googleapis` SDK dependency for three HTTP calls) and `PendingOAuthProvider` (throws a clear `503`, same "disclosed, not faked" posture as `PendingPaymentProvider`/`PendingEmailProvider`). Authorization Code flow **with PKCE** (RFC 7636) — not optional here the way it might be for a confidential server-side client, because `GET /auth/google` has no session yet to bind the flow to; `state` (compared against an httpOnly cookie) and `code_verifier`/`code_challenge` (S256) together are what stand between a stolen/replayed authorization code and nothing useful happening with it. Calls Google's `userinfo` endpoint with the freshly-issued access token rather than verifying the ID token's JWT signature locally against Google's JWKS — simpler, no new JWT-verification dependency, and adds nothing a real server-to-server TLS call to Google hasn't already guaranteed.
3. **`AuthService.loginWithGoogle`** — rejects an unverified `email_verified` claim outright (the exact "an OAuth provider vouching for an unverified email" account-takeover vector); otherwise resolves an existing `OAuthAccount` by `(provider, providerAccountId)`, falls back to matching an existing `User` by email (safe specifically because Google already vouched for that email — this is what makes it a legitimate account-linking signal rather than a guessable one), and only creates a new `User` (no `passwordHash`) when neither exists. A disabled account is rejected with the identical generic error a disabled account gets via password login — Google sign-in must not become a side channel that behaves differently.
4. **`AuthController`** — `GET /auth/google` (redirect to Google, sets state/PKCE cookies) and `GET /auth/google/callback` (verifies state, exchanges the code, logs in, redirects to a **fixed, server-configured** `STOREFRONT_BASE_URL` — never a client-supplied redirect target, which would be an open-redirect vulnerability). Both are top-level browser navigations, not JSON endpoints: every failure path (Google denies consent, malformed request, state mismatch, exchange failure, email unverified, disabled account) redirects back to the storefront with one of a small, fixed set of `authError` reason codes — Google's own `error` query value is never echoed into the redirect Location header, since passing external input into one is exactly how injection bugs happen. Both routes are `@ApiExcludeEndpoint()` (never part of the generated OpenAPI document/typed client — a browser redirects here, no JSON API client ever calls them) and not rate-limited the way `/auth/login` is (SECURITY.md §4's list names credential-guessing endpoints specifically; this one takes no credentials, only redirects).
5. **`packages/config/src/env.ts`** — `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`GOOGLE_OAUTH_REDIRECT_URI`/`STOREFRONT_BASE_URL`, all optional; `IdentityModule`'s factory requires all four together before constructing `GoogleOAuthClient` (mirrors `STRIPE_SECRET_KEY`+`STRIPE_WEBHOOK_SECRET`'s existing "required together, checked in the factory" pattern). `STOREFRONT_BASE_URL` deliberately has no dev default, unlike a structural knob — it's a real per-environment value in `CORS_ALLOWED_ORIGINS`'s category, and a wrong default silently redirecting a real user's session cookie to the wrong host in production is worse than the feature failing to boot.

**Log redaction, live-caught (`apps/api/src/common/pino-redact.ts`, `sanitize-url.ts`):** the live walkthrough below caught Google's OAuth authorization code sitting in plaintext in `req.query.code` on `GET /auth/google/callback` — added to the existing ADR-032 `redact` list. A second pass found the *raw* `req.url` (pino-http's default serializer logs both the parsed query object and the full original URL string separately) still contained it verbatim — plain field-removal `redact` can't reach into a substring of one field, only remove it whole. A `serializers.req` override that stripped the query string from `url` entirely was tried first and confirmed to close that, but it also silently dropped `remoteAddress`/`remotePort` from every log line for reasons that would have needed a deeper pino-http-internals investigation to pin down — reverted. The fix that shipped instead never touches `serializers` at all: `redact`'s `censor` option (a function, not just `remove: true`) is given `req.url` as one of its paths, and for that one path returns `redactSensitiveQueryParams(value)` — a small shared regex helper (`sanitize-url.ts`) that replaces only the `code=` value in place, leaving the path and every other query param (including `state`) intact — while every other redacted path (cookies, `x-csrf-token`, `query.code`, `set-cookie`) still returns `undefined` from the same censor function, which removes the key exactly as `remove: true` did. `AllExceptionsFilter` had the identical gap independently — it builds its own log line and JSON `path` field directly from `request.url`, entirely bypassing pino-http's redact config — and now runs the same `redactSensitiveQueryParams` helper before using it either way, so any future exception on any route with a sensitive query parameter is covered too, not just this one.

**Consequences:**

- `docs/ROADMAP.md` marks Google sign-in implemented as an optional extension beyond the auth entry point; registration/password-reset for the *password* path remain explicitly unbuilt, unaffected by this.
- `docs/DATABASE.md` §9 documents the migration.
- No admin/storefront UI was built — no "Sign in with Google" button exists anywhere yet; this checkpoint is the backend mechanism only, same boundary ADR-032 drew for password login (`apps/admin`'s login page is a pre-existing disabled placeholder, `apps/storefront` has no auth page at all yet).
- New tests: `google-oauth.provider.spec.ts` (unit — PKCE/state randomness, real Google endpoint URLs, mocked `fetch` for the token/userinfo exchange, `PendingOAuthProvider` throwing), `auth.service.spec.ts` additions (unit — unverified email rejected before touching the database, existing-account-by-sub login, link-by-email, auto-create with no `passwordHash`, disabled account via Google), `auth.controller.spec.ts` additions (real Nest app + Supertest + real guards — cookie attributes on `/auth/google`, every `authError` failure path, the 503-when-unconfigured path), `auth.integration.spec.ts` additions (Testcontainers, real Postgres — the real `@@unique([provider, providerAccountId])` constraint, real nullable `passwordHash` column, real linking-by-email against a real password-based fixture), and — from the log-redaction fix — `sanitize-url.spec.ts` (the regex helper, including a "postcode" false-positive guard), `pino-redact.spec.ts` (a real `pino()` logger with the exact production redact config and a captured output stream, proving `remoteAddress`/`remotePort` survive), `request-logging.spec.ts` (a real Nest app + real pino-http + a real HTTP request to a route shaped like the callback, asserting a fake code never reaches captured log bytes — the literal regression case), and `all-exceptions.filter.spec.ts` (new file — the filter's own hand-built log message and JSON `path` are both sanitized).
- **Verified (not asserted):** `pnpm --filter @ame-de-fil/api test` (363 tests, 36 new relative to ADR-032's baseline) and `test:integration` (25 tests, 5 new) pass, as do workspace-wide `pnpm lint`/`pnpm typecheck`/`pnpm build`, and `export-openapi.js` confirms `/auth/google`/`/auth/google/callback` are correctly absent from the generated document. Live against the real compiled API and real local Postgres, with `STOREFRONT_BASE_URL` set and Google credentials deliberately left unset: `GET /auth/google` → `503` (not configured, no cookies set); `GET /auth/google/callback?error=access_denied` → redirect with `authError=google_denied`; a request with no state/PKCE cookies at all → `authError=invalid_request`; a forged `state` query param against a real cookie → `authError=state_mismatch`, provider never called; a correctly-matching `state` → reaches the exchange step and fails with `authError=oauth_failed` only because there is no real Google to talk to (`PendingOAuthProvider`) — proving the full guard/cookie/state-verification path is real up to the point where it would actually talk to Google. A second live pass after the log-redaction fix confirmed a real callback request's `code` value absent from captured logs entirely (`req.url`, `req.query`, and the auto-logged headers) while `state` and `remoteAddress`/`remotePort` remained. **Not verified:** an actual end-to-end sign-in against Google's real servers — no Google Cloud OAuth client was available in this environment, matching the "stub/fallback only for now" scope decision made before this checkpoint started.

## ADR-034: Image storage — Cloudinary ✅ — **decided 2026-09-11**

**Context:** `ProductImage` (`url`, `position`, `altTextSv`/`altTextEn`) has existed in the schema since early on, and the public storefront API already reads and serves it — but there was no way to ever create one. No admin endpoint, no admin UI, no file-upload plumbing anywhere in the repo. ADR-020 recorded the image storage vendor as explicitly deferred alongside the deployment target and email vendor (2026-09-08). Asked directly which vendor to use; chose Cloudinary over S3/R2 and Vercel Blob.

**Decision:**

1. **Upload is backend-mediated, not direct-browser-to-Cloudinary.** The admin browser sends `multipart/form-data` to the API; the API uploads the buffer to Cloudinary server-side via `cloudinary.uploader.upload_stream`. A signed/unsigned direct-to-Cloudinary upload would bypass this codebase's CSRF guard, permission checks, and audit logging — every other mutation in this app goes through the API, and images are no exception.
2. **`ImageStorageProvider`** (`apps/api/src/catalog/images/image-storage.provider.ts`) — the same provider-abstraction pattern as `PaymentProvider`/`EmailProvider`/`GoogleOAuthProvider` (ADR-014/ADR-031/ADR-033): `CloudinaryImageStorageProvider` and `PendingImageStorageProvider` (throws a clear `503`, same "disclosed, not faked" posture). Wired into `CatalogModule` directly via a `useFactory` provider (not its own top-level module — this provider is catalog-only, unlike Payments/Notifications which cross module boundaries).
3. **Schema** — one additive migration, `20260911142948_add_product_image_cloudinary_public_id`: `ProductImage.cloudinaryPublicId` (nullable `String?`), needed to delete/transform the Cloudinary asset later (deriving a public_id back out of a URL is fragile, so it's stored explicitly rather than derived).
4. **Endpoints** — folded into the existing `AdminProductsController`/`AdminProductsService` rather than a new sub-resource controller (there's no precedent for one, and variant edits are already folded into the general product `PATCH`): `POST /admin/products/:id/images` (multipart, 5MB max, JPEG/PNG/WebP only), `PATCH /admin/products/:id/images/:imageId` (alt text), `DELETE /admin/products/:id/images/:imageId` (deletes the Cloudinary asset before the DB row — if the external delete fails, the row is kept and the error surfaced, rather than orphaning the asset with nothing left pointing at it). All three reuse the existing `products.update` permission (its own doc-comment already scopes it to "translations/status/categories/collections/variant fields" — images are the same category of edit, not a new operationally-distinct concern the way `inventory.adjust` was).
5. **`packages/config/src/env.ts`** — `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET`, all optional, checked together in `CatalogModule`'s factory before constructing `CloudinaryImageStorageProvider` (mirrors `STRIPE_SECRET_KEY`+`STRIPE_WEBHOOK_SECRET`'s "required together, checked in the factory" pattern).
6. **Admin UI** — `apps/admin/src/components/product-images-form.tsx`, rendered only on the Product Detail page (images are `productId`-scoped, so they can't be attached during Create Product — the create flow already ends with a redirect to the detail page). A responsive grid of image cards (thumbnail, per-locale alt text with its own Save, a delete button behind a confirmation dialog — irreversible, matching this project's established "confirm, don't offer undo" posture for destructive admin actions) plus an upload dialog.
7. ~~**Reordering is out of scope for this pass.**~~ **Added 2026-09-12:** `PATCH /admin/products/:id/images/order` accepts the full, ordered list of a product's image ids (rejecting anything short of exactly that set) and reassigns `position` from array order in one transaction — a full-list replace rather than a single "move to position N" edit, so the server and an optimistic client-side reorder can never disagree about everyone else's position afterward. Registered ahead of `PATCH :id/images/:imageId` in the controller (same route-ordering hazard as `inventory.controller.ts`'s `"low-stock"`/`"reservations"`/`"movements"`, ahead of its own `:variantId"`). Admin UI: move-up/move-down buttons per image card (`product-images-form.tsx`) — plain buttons, not drag-and-drop, since no drag-and-drop library exists anywhere in this repo and arrows need none.

- `docs/ROADMAP.md` and ADR-020 updated to drop "image storage vendor" from the still-open/deferred list.

## ADR-035: Self-service password registration, email verification, password reset, and a Google-linking account-takeover fix ✅

**Context:** ADR-032 deliberately left registration/password-reset unbuilt ("there is currently no way to create a `User` row at all outside a direct DB insert"); ADR-033 built Google sign-in as the one real signup path. A full production-grade auth review was requested: close the registration gap, gate checkout on proven email ownership for password accounts, and audit the existing Google flow and session/CSRF/rate-limit/cookie posture for anything registration's mere existence would newly break. Three deep research passes (session/cookie/CSRF/rate-limit infra; checkout authorization + email-template infra; testing/migration conventions) plus a dedicated design pass preceded any code — see the plan this checkpoint executed. Extends the existing stack in place: no new auth library, no session-model change, no rewritten checkout.

**The load-bearing finding:** registration's mere existence turns Google sign-in's harmless "link an existing `User` row by verified email" (ADR-033) into an account-takeover vector — an attacker can register `victim@example.com` with a password they control; when the real owner later signs in with Google for the first time, `findOrCreateUserForGoogle` would hand them a session for a row whose password the attacker already knows. This is fixed in the same change that adds registration (point 5 below), not deferred.

**Decision:**

1. **One token model**, `AccountActionToken` (`packages/database/prisma/schema.prisma`, migration `20260914083336_add_account_action_token`) — `userId`, `purpose` (enum `EMAIL_VERIFICATION | PASSWORD_RESET`), `tokenHash` (SHA-256, hashed-at-rest — mirrors `OrderStatusToken`'s existing precedent for "a bearer credential with no session/cookie behind it," deliberately unlike `Session.id`'s plaintext-PK convention), `expiresAt`, `consumedAt?`. One model, not two, per the "don't duplicate concepts" instruction — `purpose` is the only axis that varies. Issuing a new token invalidates any prior unconsumed one of the same purpose (`updateMany` then `create`, the same idiom as `SessionService.revokeSession`); consumption is a single conditional `updateMany` (`consumedAt IS NULL AND expiresAt > now()`), race-safe by construction since `tokenHash` is unique. `EMAIL_VERIFICATION_TOKEN_TTL_HOURS` (24h) / `PASSWORD_RESET_TOKEN_TTL_HOURS` (1h) — reset is short-lived since it directly authorizes taking over authentication.
2. **Email normalization**, previously nonexistent anywhere in the app: `apps/api/src/common/normalize-email.ts` (`trim().toLowerCase()`) + a shared Zod schema, applied on every write/read path touching `User.email` (register, login, forgot-password, resend-verification, Google find-or-create, admin user creation). Shipped with a same-release, hand-written data-only migration (`20260914083639_normalize_user_email_case` — the sanctioned exception to "generate, never hand-write," since Prisma has no DSL for a data-only `UPDATE`), with a pre-flight guard that aborts if lowercasing would collide two existing rows.
3. **Argon2id parameters pinned explicitly** (`password.service.ts`: `memoryCost=65536, timeCost=3, parallelism=4`) — today's implicit library defaults, now locked so a future `argon2` major bump can't silently weaken every new hash.
4. **Checkout gating** — `AuthContext`/`SessionService.validateSession` now carry `emailVerifiedAt` (zero extra queries — already joins `session.user`); a new `EmailVerifiedGuard` + `@RequireVerifiedEmail()` decorator, structurally identical to the existing `PermissionsGuard` (opt-in metadata, no-op when absent, reads `request.auth`), registered as a 5th global `APP_GUARD` between `PermissionsGuard` and `CsrfGuard`. Applied only to `CheckoutController.initiate()` — never to cart, which stays guest-friendly. A guest (`request.auth` undefined) always passes; an authenticated-but-unverified caller gets a distinct `403 { error: "EmailNotVerified" }`, not a generic 401/403, so the storefront can branch on it. `emailVerifiedAt` is optional (not required) on `AuthContext` specifically so the many pre-existing hand-built `AuthContext` test literals elsewhere in the codebase — unrelated to email verification — didn't all need updating; the guard treats `undefined` and `null` identically.
5. **The Google-linking fix**: in `findOrCreateUserForGoogle`, when an existing row is matched by (normalized) email with `emailVerifiedAt === null`, Google's verified-email claim is now treated as authoritative over the unproven password claim — before returning the row, its `passwordHash` is nulled and all its sessions revoked, atomically with setting `emailVerifiedAt`, inside one transaction. An already-verified row is left untouched (a legitimate second login method being linked, not a takeover situation).
6. **`AuthService` extended in place** (not a parallel service — every new method needs the same dummy-hash/generic-error posture, `PasswordService`, and `SessionService.revokeAllSessionsForUser` it already owns): `register`, `verifyEmail`, `resendVerification`, `requestPasswordReset`, `resetPassword`.
   - `register` is enumeration-safe and **never auto-logs-in**: an existing email hashes-and-discards the submitted password (timing parity) and returns the identical generic `201`, no session/cookie either way — a present-or-absent cookie would itself be a distinguishable signal a response message can't hide. **Also race-safe against a genuine concurrent duplicate registration**: the initial `findUnique` can't prevent two simultaneous requests both reaching `tx.user.create`, so the real Postgres `User_email_key` unique-constraint violation (caught via the existing, already-shared `isUniqueConstraintViolation` helper from `checkout/prisma-errors.ts`) is treated identically to the pre-existing-email branch — never a raw 500. Caught by a real Testcontainers integration test, not written speculatively.
   - `resendVerification`/`requestPasswordReset` are enumeration-safe (identical generic response regardless of account existence/state); a Google-only account (`passwordHash: null`) silently gets no reset email either — never revealing *how* an account authenticates.
   - `resetPassword` consumes the token before hashing (an invalid/expired token is an honest, specific `400 InvalidOrExpiredToken` — unlike the email-facing endpoints, the sensitive axis here is a possessed bearer token, not a guessable email, so vagueness buys nothing), then in one transaction sets the new hash, backfills `emailVerifiedAt` if still null (a successful reset via an emailed token is equally strong proof of ownership as a verify-email click), and calls the pre-existing `SessionService.revokeAllSessionsForUser` — no new session-service method needed.
   - No new `UserStatus` value: `status` stays `ACTIVE`/`DISABLED` (can this account authenticate at all); `emailVerifiedAt IS NULL` is the sole, orthogonal signal for "can this account check out." An unverified password user can log in, browse, and see `/account` — only checkout is blocked.
7. **`AuthController`** — five new `@Public()` endpoints, all `@RateLimit({windowMs:60_000,max:5})` except `verify-email`: `POST /auth/register`, `POST /auth/verify-email`, `POST /auth/resend-verification`, `POST /auth/forgot-password`, `POST /auth/reset-password`. `verify-email`/`reset-password` are `POST`, not `GET`, even though reached via an emailed link — the link points at a storefront page whose own client-side JS makes the real call, avoiding the classic failure where an email security scanner GETs the link and burns the single-use token before the real user clicks it.
8. **Email templates** (`packages/email/src/email-verification.ts`, `password-reset.ts`) follow `shipping-notification.ts`'s existing "caller builds the URL, template just renders a `Link`" pattern exactly. `NotificationsService` gains `sendVerificationEmail`/`sendPasswordResetEmail` (plaintext token passed directly as a parameter — never persisted, never re-derived), builds the link from `STOREFRONT_BASE_URL` (skips render and goes straight to `markFailed` if unset — never a hardcoded dev URL, matching ADR-033's Google-flow posture), and deliberately skips the two existing methods' `wasAlreadySent` idempotency guard — a resend is a deliberate new action, not a replay to dedupe.
9. **Storefront** (`apps/storefront`) — new pages/components: `create-account`, `verify-email`, `forgot-password`, `reset-password`, a self-contained `ResendVerificationButton` (resolves its own identity via `GET /auth/session` rather than requiring callers to plumb the current user's email down to it) used from both the account-page banner and checkout's `EmailNotVerified` error state. `login-form.tsx` gains "Create an account"/"Forgot your password?" links; deliberately no "unverified — resend?" state on login itself, since an unverified password account still logs in successfully. New localized pathnames added to `i18n/routing.ts`.

**Alternatives considered:** two separate token models for verification/reset (rejected — identical lifecycle, `purpose` is the only real axis, mirrors `OrderStatusToken` closely enough that a second table would be pure copy-paste drift risk); a new `PENDING_VERIFICATION` `UserStatus` (rejected — would either block an unverified user's session entirely via `validateSession`'s existing `status !== ACTIVE` check, contradicting "unverified users can still browse," or require special-casing it everywhere `status` is read for no gain over reading `emailVerifiedAt` directly); auto-login on registration (rejected — the enumeration-safety argument above); a GDPR consent checkbox at password signup (rejected for parity — Google auto-registration captures none either; adding one only here would be new, inconsistent friction, not closing a gap).

**Consequences:**

- Session tokens stay opaque/DB-revocable (ADR-015, unchanged); cookie flags stay `httpOnly`+`Secure`(prod)+`SameSite=Lax` (unchanged); the double-submit CSRF pattern is unchanged — all five new endpoints are `@Public()`, so none needs a CSRF header, same as `/auth/login`.
- Explicitly out of scope, matching existing disclosed limitations rather than introducing new ones: a per-account (vs. per-IP) rate-limit dimension and a Valkey-backed distributed rate-limit store (`docs/SECURITY.md` §4 already discloses per-IP-only as accepted); session IP/UA-anomaly logging; MFA/TOTP activation; storefront automated test infrastructure (none exists in this repo today); a common-password blocklist (`passwordStrengthSchema` is length-only, min 10, current NIST 800-63B guidance); letting an already-Google-linked user *add* a password to their own account from `/account` (a real, desirable feature, but its own endpoint, deliberately not bundled here since it would reopen the exact takeover shape point 5 closes).
- New tests: unit — `auth.service.spec.ts` additions (register new/existing-email/concurrent-P2002, resend/forgot eligibility branches, reset happy/invalid/expired/preserves-existing-verifiedAt, verify, the Google-takeover fix), `password.service.spec.ts` (explicit params embedded in the hash), `session.service.spec.ts` (`emailVerifiedAt` propagation), new `account-action-token.spec.ts` (mirrors `order-status-token.spec.ts`), new `email-verified.guard.spec.ts`, `notifications.service.spec.ts` additions (both new send methods, including the unset-`STOREFRONT_BASE_URL` → `FAILED` path), `checkout.controller.spec.ts`/`checkout.service.spec.ts` fixture-literal + new `EmailNotVerified` cases. Integration (Testcontainers, real Postgres) — new `registration.integration.spec.ts` (concurrent duplicate registration, concurrent verify-email token-consumption race, email-normalization-against-existing-row), new `password-reset.integration.spec.ts` (real `expiresAt` comparison, already-consumed token, real session revocation, real re-login with the new password, verifiedAt backfill), `auth.integration.spec.ts` additions (the Google-takeover fix against a real seeded row). `seedUserWithPermissions` fixture gained an `emailVerifiedAt` option (default `null`, matching a real fresh registration); new `seedAccountActionToken` fixture.
- **Verified (not asserted):** `pnpm --filter @ame-de-fil/api test` — 755 tests pass (workspace-wide, up from the pre-checkpoint baseline). `test:integration` — 118 tests pass, including all new registration/password-reset/Google-takeover specs against real Postgres. `tsc --noEmit`/`eslint` clean across `apps/api`, `apps/storefront`, `packages/database`, `packages/email`, `packages/config`, `packages/types` (one pre-existing, unrelated failure in `marketing/admin-homepage-sections.service.spec.ts` confirmed via `git log` to predate this checkpoint, left untouched). `export-openapi.js`/`packages/types`' generated client confirm all five new `/auth/*` paths. Live, real end-to-end browser walkthrough (Playwright) against the compiled API, real Postgres, and real Mailpit: register → real verification email received and its link followed → account page banner disappears → forgot-password → real reset email received and followed → **old session confirmed revoked** (redirected to login) → login with the new password succeeds → still verified. A second account: registered, left unverified, added a product to cart, attempted checkout → real `403 EmailNotVerified` surfaced in the UI with a working resend action → resend confirmed via a fresh Mailpit message. Guest checkout confirmed unaffected (pre-existing + new guard-level tests). **Local dev environment gaps found and fixed as part of verifying this**, unrelated to the auth work itself: `apps/api/.env`'s `STOREFRONT_BASE_URL` had a missing closing quote (crash-looping the dev server on every restart via a `ZodError`) and `SMTP_HOST`/`SMTP_PORT` were never pointed at the local Mailpit container `docker-compose.yml` already documents — both fixed in the (gitignored, local-only) `.env` file, not committed.

## ADR-036: Email one-time-code (OTP) login — a second, parallel login method, additive only ✅

**Context:** requested as an additional storefront login method alongside the existing email+password flow (ADR-032/ADR-035), explicitly **not** a replacement — password signup, email verification, password reset, and Google sign-in all stay exactly as they were. Shopify's Customer Accounts login (`shopify.com/authentication/.../login`) was reviewed as an interaction-pattern reference only (email-first, progressive disclosure, a 6-box code screen) — its visual design (generic SaaS chrome, Shopify's own purple accent) was explicitly not carried over; Âme de Fil's existing cream/serif/bordered identity is unchanged.

**Decision:**

1. **A separate model, `LoginOtp`, not a third `AccountActionTokenPurpose`.** `AccountActionToken.tokenHash` is globally `@unique`, which only holds because a 256-bit token's collision odds are ~zero — a 6-digit code has just 1,000,000 possible values, so a global unique constraint would throw a real `P2002` the first time two different users happened to hold the same code at once. `LoginOtp.codeHash` is therefore deliberately **not** unique; every lookup is scoped by `userId` too. It also needs something `AccountActionToken` has no concept of at all: a per-code `attempts` counter (5 max) — a low-entropy, human-typed code needs attempt-limiting as its primary defense, unlike a 256-bit token that's never brute-forced digit-by-digit. Migration: `20260914102019_add_login_otp`.
2. **Parameters, all as decided upfront, no discovery needed:** `crypto.randomInt` (never `Math.random`) for the 6 digits, 10-minute expiry (`LOGIN_OTP_TTL_MINUTES`, configurable, unlike the fixed attempt/cooldown constants below), 5 max attempts, 60-second resend cooldown enforced **server-side** (checked inside `requestLoginOtp` itself, not just a disabled button client-side — this is also the real defense against spraying a victim's inbox from many IPs, which per-IP rate limiting alone can't stop), one active code per user (requesting a new one invalidates the prior unconsumed one, same `updateMany`-then-`create` idiom `issueAccountActionToken` already uses), SHA-256 hash-at-rest only (still worth doing as defense-in-depth against a DB leak during the code's live window, but — unlike the 256-bit tokens — entropy is explicitly **not** the primary control here; attempt-limiting + short TTL are). Request rate-limited 5/min/IP, verify 10/min/IP (`AuthController`).
3. **`AuthService` extended in place again** (not a parallel service, same reasoning as ADR-035): `getLoginMethod`, `requestLoginOtp`, `loginWithOtp`, reusing `SessionService.createSession`/`issueSession` completely unchanged — an OTP-issued session is indistinguishable from a password- or Google-issued one downstream (same cookies, same revocation, same `validateSession` checks).
   - `getLoginMethod` is a **pure UI-branching hint** (`{ method: "password" | "otp" }`), no side effects. The one accepted, bounded enumeration trade-off in this whole feature: it necessarily reveals "does this email have a password" (a single bit) to support the email-first progressive-disclosure UX — a Google-only account and a wholly nonexistent email are never distinguished from each other, both get `"otp"` alike, and this was raised and accepted explicitly (see `SECURITY.md` §1) rather than discovered after the fact.
   - `requestLoginOtp` is enumeration-safe (identical generic response regardless of account existence/state, mirrors `resendVerification`/`requestPasswordReset`) — **and**, unlike password reset, a Google-only account **is** eligible: their email is already verified via Google, so an email-OTP is an equally strong proof of ownership, meant as a real alternative login method for them, not just a password-account fallback.
   - `loginWithOtp` backfills `emailVerifiedAt` on success if still null (same free unblock-of-checkout bonus `resetPassword` already gives) and is race-safe on both axes: wrong-guess attempt-incrementing is a single atomic SQL `attempts = attempts + 1` (no read-modify-write), and correct-code consumption is the same conditional-`UPDATE`-wins-the-race idiom as `consumeAccountActionToken`. **A real bug was caught here by the integration test, not written speculatively**: the emailVerifiedAt backfill originally updated the database but then passed the stale pre-update `user` object into `issueSession`, so the very login response that just verified the email still reported `emailVerifiedAt: null`. Fixed by using the `update()` call's own return value; a unit test now pins this exact regression shape (mocks `user.update` to return a distinctly-verified row and asserts the *returned* session user reflects it, not just that the update call happened).
4. **Email template**: `packages/email/src/login-otp.ts`, no link/URL at all (unlike verification/reset) — the code itself is the whole payload, so `sendLoginOtpEmail` needs no `STOREFRONT_BASE_URL` dependency, one less local-dev configuration footgun than the other two. The code is also placed in the subject line (`"123456 is your Âme de Fil sign-in code"`) — the one email type here where inbox-preview glanceability without opening the message is worth more than a generic subject, matching common real-world OTP-sender practice.
5. **Storefront**: `login-form.tsx` becomes the email-first orchestrator (owns `email`/`step` shared state across three screens: email → password-or-otp), with the password and OTP screens split into their own files (`login-password-step.tsx`, `login-otp-step.tsx`) since each owns real form state the orchestrator doesn't need. `otp-code-input.tsx` — six real accessible `<input>`s (not one hidden input behind decorative boxes), each with its own `aria-label`, `autoComplete="one-time-code"`, and `inputMode="numeric"`; auto-advances focus on entry, auto-retreats on backspace into an empty box, and a paste of a full 6-digit code anywhere in the group fills every box and auto-submits — matching the "auto-focus, paste support, auto-submit after the sixth digit" requirement exactly. "Continue with Google" appears only on the first (email) screen, never on the password/OTP sub-screens. Visual identity: the existing `Card`/serif-`Heading`/bordered-`Input` shell throughout — no new visual language introduced for this feature.

**Alternatives considered:** reusing `AccountActionToken` with a third `purpose` (rejected — the collision-safety argument in point 1); a client-side-only resend cooldown (rejected — trivially bypassed, and the server-side version doubles as the real anti-spray defense); revoking other sessions on a successful OTP login (rejected — OTP is a login event like password/Google, not a credential-change event like password reset; no existing login path revokes other sessions either).

**Consequences:**

- Zero changes to `AccountActionToken`, `EmailVerifiedGuard`, `CsrfGuard`, `SessionAuthGuard`, `PermissionsGuard`, the checkout gate, or any of ADR-035's endpoints — this feature is purely additive, verified by re-running the full pre-existing suite unchanged (see below) alongside the new tests.
- `AuthContext`/`Session`/cookie shape are all unchanged — an OTP-issued session is byte-for-byte the same shape as any other.
- Explicitly out of scope, consistent with ADR-035's own disclosed list: a per-account rate-limit dimension; SMS-based OTP (email only, per the request); allowing OTP to double as a signup/verification path (explicitly login-only — a brand-new email requesting a code still creates no `User` row, per point 2's enumeration-safety design; the existing register → verify-email flow is untouched).
- New tests: unit — `login-otp.spec.ts` (code generation/hashing, mirrors `order-status-token.spec.ts`), `auth.service.spec.ts` additions (`getLoginMethod` branching including the accepted enumeration bound, `requestLoginOtp` eligibility/cooldown/enumeration-safety, `loginWithOtp` happy path + the emailVerifiedAt-backfill regression + wrong-code/attempt-increment/max-attempts-kills-code/no-current-code/nonexistent-email/disabled-account/race-loses, all asserting the identical generic error), `auth.controller.spec.ts` additions (all three new routes' cookie behavior, rate limits, malformed-body 400s), `notifications.service.spec.ts` additions (`sendLoginOtpEmail`, including proving no `STOREFRONT_BASE_URL` dependency). Integration (Testcontainers, real Postgres) — new `login-otp.integration.spec.ts`: real expiry, real atomic attempts increments culminating in a real code-kill at the 5th wrong attempt, a real concurrent-verification race (exactly one of two simultaneous correct submissions wins), real cooldown-blocks-a-second-issuance, real new-code-invalidates-old-code, and enumeration-safety against a real nonexistent email. New `seedLoginOtp` fixture (mirrors `seedAccountActionToken`, with a `createdAt` override needed specifically to backdate a seeded code past the resend-cooldown window for the invalidation test).
- **Verified (not asserted):** `pnpm --filter @ame-de-fil/api test` — 791 tests pass (up from ADR-035's 755; two genuine test-design bugs surfaced and fixed while writing these — a resend-cooldown/fixture-timing conflict, and an `updateMany`-vs-`update` assertion mismatch — neither was an implementation defect). `test:integration` — 126 tests pass (up from 118), including every new OTP integration case above. `tsc --noEmit`/`eslint` clean across `apps/api`/`apps/storefront`/`packages/email`/`packages/database`/`packages/config`/`packages/types` (same one pre-existing, unrelated `marketing/admin-homepage-sections.service.spec.ts` failure, untouched). `export-openapi.js`/`packages/types`'s generated client confirm all three new `/auth/*` paths. Live, real end-to-end browser walkthrough (Playwright) against the compiled API, real Postgres, and real Mailpit: email-first screen → existing password account → password sub-screen renders with a working "Email me a code instead" link → OTP screen renders on-brand (cream/serif/bordered, not Shopify's chrome) with a live 60s countdown → real code fetched from Mailpit (also confirmed correctly localized to the account's own locale, and present in the subject line) → typed across the six boxes → **auto-submitted on the sixth digit** → real session issued, landed on `/account`. Separately: a wholly unknown email through the same flow correctly proceeds straight to a real OTP screen with no distinguishable difference (enumeration-safety observed directly in the UI, not just asserted in a test) → an intentionally wrong code produced the exact inline error text with all six boxes reset and marked invalid, matching the low-drama error treatment specified. Existing, untouched flows spot-checked live in the same session: `/create-account` and `/forgot-password` both still render and behave identically to before this feature.
